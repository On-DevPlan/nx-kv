# A02 · SOP · 领取任务与扩展任务的上下文知识

> 命中信号：拿到一条任务要开始干 / 交付给 agent 的提示词不对（少了一段、变量是空的）/
> 要给 agent **多一条上下文知识**（流程规则、仓库说明、必须遵守的约束）/
> 上下文散在好几处，想知道「交付里到底有什么」。
>
> 本篇是 A 序列里**最常走的一条**：先 `get` 拿到交付，再照交付里的要求干；
> 要改「交给 agent 的东西」时，这里给的是**落点与规矩**（知识在哪、怎么加、加完怎么验）。
> 区块 / 变量 / 引擎的细节查 `B03-提示词模板与上下文.md`。

## ① 前置：先把现场看清楚

```powershell
node bin/kv.mjs localtask get --cwd "<项目目录>"                    # 领一条（无活时阻塞到超时）
node bin/kv.mjs localtask get --cwd "<项目目录>" --timeout 60       # 指定阻塞上限（**秒**；缺省用项目配置）
node bin/kv.mjs localtask get --cwd "<项目目录>" --param k=v       # 带外部参数（进交付 ctx：{{k}} / {{params.k}}）
node bin/kv.mjs localtask preview --id <id>                        # 零副作用：看这条会交付什么
node bin/kv.mjs localtask show --id <id> --cwd "<项目目录>"        # 看这条任务本体（含附件清单与本地路径）
```

`get` 的三个关键点：

| 点 | 说明 |
|---|---|
| **默认输出就是交付原文** | 读原文别用 `--json`（`--json` 是给程序用的形状，不是逐字原文） |
| **拿到就要按段落执行** | 交付里的 `ack` 段写明「完成后必须调用 `localtask done --id <id> --summary "…"`」 |
| **阻塞 ≠ sleep** | `--timeout N`（**秒**）是服务端挂住请求到点返回 timeout，不是让你自己等（见 `B03-提示词模板与上下文.md`） |

## ② 判定：这条上下文知识该落在哪

**先问它是「事实」还是「规则」**——落点完全不同：

| 知识的性质 | 落点 | 谁写 | agent 怎么看到 |
|---|---|---|---|
| 某个仓库 / 组 / 参考仓库的**事实**（介绍、定位、说明、文档） | 文档库（refs）+ 挂到宿主 | 人（面板）或 agent（`docs ref add` / `docs bind`） | 交付 `{{nx-kv.context}}` 段 |
| **流程控制**（按什么顺序做、什么不能做、何时必须回填） | 提示词区块（ctx 字段 + 模板） | 改代码 | 交付里多一段 |
| 某条任务**独有**的要求 | 任务正文（frontmatter / 正文） | 发布者 | 任务正文本身 |
| **运行时状态**（时间目标、闸门、剩余量） | goal / 编排插件 | 改代码 | `{{nx-kv.timecheck}}` / `{{nx-kv.doneguard}}` 段 |

判错的后果：**事实写成规则** → 每次交付都刷同样的长文；**规则写成事实** → agent 永远看不到那条约束。

## ③ 动作 A · 领一条并读懂它

1. `node bin/kv.mjs localtask get --cwd "<项目目录>"` 领取；无活时它会阻塞到 `--timeout`。
2. 逐段读交付：`<nx-kv.context>`（仓库/组/参考仓库）、`<nx-kv.attachment>`（附件怎么取）、
   `<nx-kv.timecheck>` / `<nx-kv.doneguard>`（时间目标与完成门禁）、`<nx-kv.ack>`（怎么回填）。
3. 有附件先按附件段的「取用方式」读：图片看图、md 读正文、**文件夹先列目录**再读里面的文件。
4. 干完后 `node bin/kv.mjs localtask done --id <id> --summary "<完成总结>"`；
   总结要能让人不点开代码就判断这事做没做完（文件清单 / 数据变化 / 入口变化 / 验证命令与结果 /
   未做事项）。
5. 队列里还有活 → 继续 `get`（别提前收尾）。

## ④ 动作 B · 扩展一条上下文知识

### B1 · 事实类 → 写成文档（不需要改代码）

```bash
node bin/kv.mjs docs ref add --owner repo --repo <仓库key> --desc "<这篇是什么>" --json
node bin/kv.mjs docs bind --repo <仓库key> --ref ref:<refId> --json      # 挂成主篇
node bin/kv.mjs docs link --board <组key> --ref ref:<refId> --note "<说明>" --json
```

挂完还要**能被模板取到**：仓库介绍 → `repo.intro`；组定位 → `group.desc`；其余文档 →
`repo.docs` / `group.docs`（模板里 `{{#each}}` 自己组织行）。
新增一条**新字段**（不是新文档）时才要改代码：`src/modules/tasktool/delivery-template.ts` 的
`deliveryCtxOf` 里加投影 → `src/shared/prompt-blocks.ts` 的默认模板里加占位 →
`src/web/frontend/page/settings/prompt-template-params.ts` 的变量速查表加一行。

### B2 · 流程控制类 → 加一个区块（ctx 字段 + 模板）

1. **取数**：要什么数据，从哪个 service 取（只读、别在 ctx 里做 IO）。
2. **投影**：在 `src/modules/tasktool/delivery-template.ts` 的 `deliveryCtxOf`（或对应域的
   `attach-template.ts` / `plugins/`）里加**纯数据**字段——ctx 只放数据，**措辞归模板**。
3. **成文**：在 `src/shared/prompt-blocks.ts` 的 `BLOCK_DEFS` 里加一个区块（id / tag / label /
   desc / defaultTemplate），或并进已有区块的默认模板。
4. **知识化**：变量清单要**两处**同步——模板的 `vars_schema`（DB 里声明，前端据此渲染表单）
   与 `src/web/frontend/page/settings/prompt-template-params.ts` 的 `BLOCK_PARAMS` 速查表。
5. **验**：见 §⑥（`preview` 看渲染结果——**变量名写错不会报错，只会静默渲染成空**）。

### B3 · 运行时状态类 → goal / 编排

时间目标、闸门、依赖这类**随状态变化**的东西走 `src/modules/tasktool/plugins/`：
插件实现 `BasePlugin` 的钩子，`definePlugin` 注册即生效（IoC，runtime 只问容器）。
详见 `A10-改编排闸门.md`。

## ⑤ 现状体检：交付上下文现在散在哪儿

写这一篇时先查了一遍（结论：**没有集中的落点，也没有自动化的变量表**）：

| 上下文域 | 装配位置 | 模板消费方 | 备注 |
|---|---|---|---|
| 任务本体（id / text / 来源 / 现状 / cwd / name） | `wait.ts` 的 `baseCtx` | `{{task.*}}` | text 交付前重排（最新轮置顶） |
| 仓库 / 组 / 参考仓库 / 其余组 | `delivery-template.ts` 的 `deliveryCtxOf` | `{{repo.*}}` `{{group.*}}` `{{refRepos.*}}` | 组材料只进**组任务**（frontmatter 带 board） |
| 附件 | `attach-template.ts` 的 `attachTemplateCtx` | `{{attach.*}}` | 按 kind 给专属子对象（file/url/task/ref/mdfile/folder） |
| 时间目标（check / 状态行 / extra） | `wait.ts` + `plugins/goal-template.ts` | `{{goal.*}}` | 领取与每轮 check **同源**渲染 |
| 外部参数 | `params.ts` → `buildDeliveryCtx` 的平面扩展 | `{{params.k}}` 或 `{{k}}` | 内建键不被覆盖 |
| 持续 get | `wait.ts` 的 `getloop` | `{{getloop.*}}` | 阻塞窗口也在同一份 ctx |
| **区块装配** | `system-blocks.ts` 的 `composeSystemBlocks` | 8 个区块按 `BLOCK_DEFS` 顺序 | 坏模板 → 回落内置 + 告警 |

**四条可优化项**（本篇按「现状」写，改动前先确认落点仍在）：

1. **ctx 装配分散在 4 处**（wait / delivery-template / attach-template / plugins）——
   想知道「交付里有什么」要读 4 个文件。
   **约定（从本篇起生效）**：**新的**上下文知识统一落在 `src/modules/tasktool/` 下的一个
   context 目录（**尚未建立**，遇到第一篇时顺手建；里面按域分文件 + 一个汇总入口）；
   已有的装配暂不动（改动面大，另起一次重构，别混在功能改动里）。
2. **变量知识化两处手写**（模板 `vars_schema` + 前端 `BLOCK_PARAMS`）→ 必然漂移。
   **建议**：由 ctx 域自己声明变量清单（每个域导出自己的 `VARS`），
   `BLOCK_PARAMS` 改为从它生成，别再手抄（需要一个生成脚本，落在 `scripts/`）。
3. **区块定义（`shared/prompt-blocks.ts`）与 ctx 装配（`modules/tasktool/`）分离**——
   区块无法声明「我需要哪些 ctx 字段」。
   **建议**：`BLOCK_DEFS` 加 `needs: ['repo','group']`，渲染前据此校验 ctx 是否齐
   （缺字段 → 告警，而不是静默空）。
4. **模板变量写错不报错**（Handlebars 未知变量渲染成空串）→ 只能靠 `preview` 看。
   **建议**：给 `validateTemplate` 加「变量是否在 ctx 契约里」的检查（配合第 3 条的 `needs`）。

> 这四条是**建议**，不是既成事实；落地前先在本篇与 `B03-提示词模板与上下文.md` 里同步口径。

## ⑥ 自检（扩展完必须逐条验）

```bash
node bin/kv.mjs localtask preview --id <id>      # 零副作用看渲染结果：变量有没有渲染成空
node bin/kv.mjs localtask get --cwd "<项目目录>"  # 真领一次，看最终交付原文
```

| 检查 | 通过判据 |
|---|---|
| 区块出现 | 交付里能看到新段（或原段多了内容），且**不是空标签**（`组定位：`这种空壳算失败） |
| 变量有值 | 模板里新占位符渲染出了真实内容，不是空串 |
| 老交付没坏 | `preview` 里原有区块的输出与改动前逐字一致 |
| 变量表同步 | 设置面板的变量速查表里能查到新变量；模板 `vars_schema` 也声明了 |
| 坏模板不炸队列 | 故意写错语法 → `preview` 告警 + 回落内置模板，**领取仍能成功** |
| 边界 | 空数据时该区块整段不出现（`{{#if}}` 闸门），而不是印一行空标签 |

## ⑦ 失败分支

| 症状 | 原因 | 处置 |
|---|---|---|
| 模板里新变量渲染成空 | 变量名写错 / ctx 没投影 / 挂在别的域下 | 先 `preview` 看渲染结果，再按 §⑤ 的表核对装配位置 |
| 交付里出现空标签（`组定位：`） | ctx 字段存在但内容为空 | 该域要么给默认文案，要么用 `{{#if}}` 整段闸掉 |
| 改了模板但交付没变 | 模板存在 `templates` 表（运行时数据），代码默认值不生效 | 看设置面板当前生效的是哪条；`preview` 确认 |
| 改了 action 但接口 404 | 路由在进程启动时编译 | `pnpm gen` 后**重启 serve** |
| 模板改坏 → 领取失败 | 模板语法错本应回落内置 | 查 `renderWarnings`；坏模板来自运行时数据时先在面板修回来 |
| 新区块每轮都刷屏 | 事实被写成了规则 | 回到 §② 判定：事实 → 文档；规则 → 区块 |
| 文档写完但交付里看不到 | 文档没挂到宿主 / ctx 没投影它 | `docs bindings --host <key>` 看是否挂上；再核对 §⑤ 的投影位置 |
| 并行会话把 ctx 改乱了 | 多个分支同时改 `delivery-template.ts` | 先 `git fetch` 对齐远端，再决定谁让谁 |

## ⑧ 反模式

- 在 ctx 里塞**成文措辞**（ctx 只放数据；措辞在模板里，用户才能改）。
- 只加模板不加变量表（用户不知道能写什么）或只加变量表不加模板（模板引用不到，等于没加）。
- 新增字段不 `preview` 就提交（变量写错不报错，只会静默变空）。
- 把「每轮都要说的规则」塞进任务正文（正文会被重排，规则会沉底）。
- 把「一次性要求」塞进全局模板（所有任务都被污染）。
- 改 `templates` 表里的运行时数据来「修」代码 bug（那是用户数据，不是代码）。
