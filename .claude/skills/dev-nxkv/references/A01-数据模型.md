# A01 · 数据模型：表、字段与身份

> A 序列 · 底层数据结构之一。回答「数据存在哪张表、每列是什么、身份怎么算」。
> 关系（谁连谁）见 [[A02-关系模型]]；配置类键位见 [[A03-键与扩展位]]。

## 1. 存储底座

| 项 | 值 |
|---|---|
| 业务数据源 | SQLite 单库（`node:sqlite`）——**唯一**，文件只存附件字节与文档正文 |
| 库文件路径 | `NX_KV_DB` 环境变量优先，否则 `<APP_DIR>/nxkv.db`（`src/core/paths.ts`） |
| Node 下限 | `>= 22.13.0`（`node:sqlite` 免 `--experimental-sqlite` 的最低版本，见 `src/core/db/version.ts`） |
| 连接 | **进程级单例**：`openStore()` / `getDb()` / `closeDb()`（`src/core/db/index.ts`）。同进程再开一条连接写同一个库 = 自己跟自己抢写锁 |
| 连接级 PRAGMA | `journal_mode=WAL` / `foreign_keys=ON` / `busy_timeout=5000` / `synchronous=NORMAL`（`src/core/db/driver.ts`，**每个连接都要设**） |
| 事务 | `txw(conn => …)`（`src/core/db/tx.ts`）；回调**同步**，里面不要 `await` 网络/文件 IO |
| 时间戳 | 一律 `nowMs()`（`src/core/db/time.ts`），不要各自 `Date.now()` |

两条最贵的教训：

- **SQLite 外键默认是关的**，且是 per-connection 的。少设 `foreign_keys=ON`，所有 `REFERENCES` 静默失效——表建得对、数据却全是脏的，而且**不报错**。
- **WAL 下直接复制 `.db` 文件会拿到不一致快照**。备份一律用 `VACUUM INTO`（走 `nx-kv db backup`）。

## 2. schema 版本与迁移机制

- 当前版本：`CURRENT_SCHEMA_VERSION = 8`（`src/core/db/version.ts`）。改 schema 就改这个数字，并加一条迁移边。
  **不要照抄本行数字**——它是快照，权威值是 `src/core/db/version.ts` 与 `ls src/core/db/migrations/`。
- 迁移区 `src/core/db/migrations/`：
  - `v1.sql` = 版本 1 的**完整 schema 快照**（历史，**永不修改**）
  - `v2.sql` / `v3.sql` / `v4.sql` = 逐版**跃迁脚本**
  - `index.ts` = 边映射（`DIRECT_EDGES`）+ 组合边 BFS + `planMigrationPath()`
  - `v2-data.ts` / `v4-data.ts` = 随边执行的数据搬运（`apply`，同事务）
- 硬规则：
  - 只升不降；缺边**直接报错**，不静默跳过。
  - **禁止修改已发布的 `vN.sql`**——它随包发布、可能被外部库执行过。
  - 新增版本 = 加 `vN+1.sql` + 在 `DIRECT_EDGES` 登记；需要搬数据时挂 `apply: migrateXxx`（同事务执行）。
  - 组合边（如 0→2）不写脚本，由直接边串联，`EDGE_MAP` 里显式登记。
- **schema 决策门禁**（`scripts/check-schema-decisions.mjs`，进 `pnpm lint`）：
  - 每张 `CREATE TABLE` 上方必须有一行 `-- @decision docs/decisions/<文件名>.md`，决策文件真实存在且 `date:` 与文件名日期前缀一致；
  - 每张 `DROP TABLE` 同样要 `@decision`，且决策文件里 `drops:` 列有这张表；
  - 最新版本快照里带 `@sunset YYYY-MM-DD` 的表，超过日落日期直接报错；
  - 每个版本 `vN.sql` 必须有一份 `docs/decisions/versions/*-vN.md` 版本说明。
  - **没有决策注释的 schema 改动过不了 lint**——写 SQL 前先想清楚决策文件叫什么。

| 边 | 文件 | 内容 |
|---|---|---|
| 0→1 | `v1.sql` | 初始 schema（topics / tasks / refs / repos / templates / meta / settings …） |
| 1→2 | `v2.sql` + `v2-data.ts` | 附件/资源统一模型：建 `attachments` / `task_attach` / `ref_attach`，删 `task_refs` / `ref_relations` |
| 2→3 | `v3.sql` | `templates` 加 `scope`（可见域 JSON 数组）与 `origin_topic`（创建来源主题） |
| 3→4 | `v4.sql` + `v4-data.ts` | 参考仓库绑定从**仓库级**升到**组级**（`group_refs`） |

**「这是不是我们的库」** 看 `meta.store_kind`，不看「表存不存在」：db 在但 `meta` 无 `store_kind` → 拒绝启动（别人的 SQLite 被改名成 `nxkv.db` 了）。`db` 不存在 → 全新或旧 JSON 待导入。

## 3. 表清单（15 张）

### 3.1 归属域：仓库与项目组

| 表 | 业务对象 | 主键 | 关键列 | 关键约束 |
|---|---|---|---|---|
| `repos` | 仓库 / 项目组 / 参考仓库 | `key`（TEXT，**非空、全局唯一**） | `type`（`repo`/`group`）、`name`、`description`、`path`（仅本机）、`remote`（仅 repo）、`ext`、`version`、`deleted_at` | `CHECK (key <> '')`；`key` 不可重用（软删后再建同名应「恢复」而非新建） |
| `repo_group_members` | 仓库组成员关系 | `(group_key, repo_key)` | `position`（组内排序）、`note`（成员在本组的说明） | 两列 FK `repos(key)`；`CHECK (group_key <> repo_key)`；组侧 `type='group'` 由写入层保证（跨表，CHECK 表达不了） |
| `group_refs` | **组级参考仓库**绑定（v4） | `(group_key, ref_key)` | `note`（组↔参考的说明）、`position` | 两列 FK `repos(key)` `ON DELETE CASCADE ON UPDATE CASCADE`；`CHECK (group_key <> ref_key)` |

`repos` 的三条铁律：

- `key` **只能**由用户显式给出，或由 `remote` 归一化（协议头去掉 / `.git` 去掉 / 转小写 / 去尾部斜杠 → `github.com/org/repo`）。**没有 remote 时必须报错让用户填**，绝不允许自动生成 `local/<目录名>`——那是拿目录当身份，换机器就撞车。
- `key` 与 `path` 是两件事：`key` 跨机器成立（导出关系靠它），`path` 只在本机成立（导出时丢弃）。
- 参考仓库**不是独立表**：DB 侧 `repos.type` 没有 `ref` 值，参考身份记在 `ext.ext_legacy_type='ref'`，对外投影成 `dev` / `ref`。

### 3.2 队列域：主题与等待态

| 表 | 业务对象 | 主键 | 关键列 | 关键约束 |
|---|---|---|---|---|
| `topics` | 本机主题（队列） | `id`；`key` UNIQUE | `repo_key`（FK，`CASCADE`）、`cwd`、`group_key`（FK，`RESTRICT`）、`next_seq`（只增不减）、`ext`、`version` | 唯一索引 `ux_topics_cwd_group` = `(cwd COLLATE NOCASE, COALESCE(group_key,'')) WHERE deleted_at IS NULL` |
| `topic_presence` | 队列等待态（跨进程） | `topic_id`（FK `topics(id)` `CASCADE`） | `waiting`、`since_ms`、`until_ms`、`cancel_requested` | 判定「真的在等」= `waiting=1` **且** `until_ms > now`（只看 `waiting` 会把被杀进程的残留当活人） |

`topics` 的口径：

- **队列身份 = `(cwd, group)`，不是 cwd 一个**。同一目录可以在多个组下各跑一摊活，各发自己的编号。
- `key` 是 `(cwd, group_key)` 的**纯函数派生值**（`src/core/topic-key.ts` 的 `topicKeyOf`），**没有任何写入入口**。旧版 key = sha1(目录名)，与新版不可互推，旧 key 一律失效（只留 `ext.ext_legacy_key` 取证）。
- `group_key` 用 `RESTRICT` 而不是 `SET NULL`：置空会让「组下队列」和「单跑队列」撞成同一个 `(cwd, NULL)`，删不删得成功取决于该目录下有没有单跑队列——这种时灵时不灵比直接报错糟得多。

### 3.3 任务域

| 表 | 业务对象 | 主键 | 关键列 | 关键约束 |
|---|---|---|---|---|
| `tasks` | 任务 | `id`；`UNIQUE (topic_id, seq)` | `status`(`pending`/`claimed`/`done`/`cancelled`)、`body`（正文）、`ext`、`feedback`/`feedback_at`、`from_src`、`blocks_following`、`claimed_at`/`done_at`、`round`（派生轮次） | `CHECK (status IN (...))`；触发器 `trg_tasks_identity` 锁住 `seq`（同队列内）与 `created_at` |
| `task_links` | 派生链（历史，append-only） | `(src_id, dst_id, type)` | `type`(`comment`/`reopen`/`feedback`)、`note` | `CHECK (src_id <> dst_id)`；唯一索引 `ux_task_links_parent ON (src_id)` ⇒ 一个任务只有一个来源 ⇒ 链是树不是网 |
| `task_deps` | 编排依赖（当前约束，可加可撤） | `(task_id, dep_id)` | — | `CHECK (task_id <> dep_id)`；两列都是**全局 `tasks.id`** |
| `goals` | 任务级时间目标 | `id`；FK `task_id` | `duration_sec`、`started_at`、`deadline`、`prompt`、`state` | `CHECK (duration_sec > 0)`、`CHECK (deadline > started_at)`；唯一索引 `ux_goals_task ON (task_id) WHERE deleted_at IS NULL` |
| `goal_checks` | 每次 check 的流水 | `id`；FK `goal_id` | `at`、`elapsed_sec`、`remaining_sec`、`overtime_sec`、`reached`、`summary` | 派生值只增不改——`deadline` 会被改，不存当日快照的话历史 check 会被重算 |

任务的四种身份，别混：

| 身份 | 载体 | 用途 |
|---|---|---|
| 全局 id | `tasks.id` | 外键 / 依赖 / 派生链 / 跨主题引用 |
| 队列内编号 | `tasks.seq` | 对外显示（`#12`）、CLI 参数 |
| 轮次 | `tasks.round` | 派生链第几轮（根 = 1） |
| 行级乐观锁 | `tasks.version` | 更新时 `WHERE version = :old` 校验递增 |

`tasks.seq` **只增不减**：编号复用会让历史引用指向另一条任务。软删的任务仍然占着编号，这是刻意的。

### 3.4 文档域

| 表 | 业务对象 | 主键 | 关键列 | 关键约束 |
|---|---|---|---|---|
| `refs` | 文档（md）索引 | `id`（TEXT） | `type`（`md`）、`locator`（稳定标识：docs 根下相对路径 / 外部绝对路径） | 索引 `ix_refs_locator ON (locator COLLATE NOCASE)`（快搜走范围扫描，不走 `LIKE 'x%'`） |
| `ref_bindings` | 文档挂到仓库/组/组内仓库 | 无 PK，唯一索引 `ux_ref_bindings (repo_key, COALESCE(group_key,''), ref_id)` | `type`(`repo`/`group`/`group_repo`)、`position`、`note` | `CHECK` 保证 `group_repo` 必有 `group_key`，其余必须为空 |

`refs` 只装 `.md`。**文档正文不在库里**，在磁盘上（`~/.nx-kv/docs/` 或外部绑定路径）；`refs` 只做稳定身份 + 孤儿清单。

文档地址 = **文件在 docs 根下的相对路径，第一段是命名空间**（`repo/` · `group/` · `ext/`）。不另造 URI 前缀，物理位置与逻辑地址是同一个字符串。任务不在其中：任务不是 ref，正文是 `tasks.body`。

### 3.5 资源域（附件）

| 表 | 业务对象 | 主键 | 关键列 | 关键约束 |
|---|---|---|---|---|
| `attachments` | 统一资源 | `id`（TEXT） | `kind`(`file`/`url`/`task`/`ref`)、`name`、`local_path`、`url`、`mime`、`size`、`hash`、`storage`(`''`/`local`/`cloud`)、`target_kind`/`target_key`/`target_seq`、`dedupe_key`、`meta` | 唯一索引 `ux_attachments_dedupe ON (dedupe_key) WHERE dedupe_key <> '' AND deleted_at IS NULL` |
| `task_attach` | 任务 ↔ 资源 | `(task_id, attachment_id)` | `role`(`inline`/`attach`/`doc`)、`position`、`note` | 两列 FK `CASCADE` |
| `ref_attach` | 文档 ↔ 资源 | `(ref_id, attachment_id)` | `role`(`inline`/`attach`/`reference`)、`position`、`note` | 两列 FK `CASCADE` |

资源 id 公式（`src/core/attachmentdb/ids.ts`，唯一实现）：

| kind | id | 说明 |
|---|---|---|
| `file` | `fileId`（32+ hex，可带扩展名） | 与正文 `![名](fileId)` 语法对齐，正文写法一字不改 |
| `url` | `att_url_<sha1(小写 url).slice(0,16)>` | 同 URL 归一 |
| `task` | `att_task_<sha1(topic_key + ':' + seq).slice(0,16)>` | 指向队列内任务 |
| `ref` | `att_ref_<sha1(ref_id).slice(0,16)>` | 指向文档 |

字节落地两处，**元数据唯一真相在 `attachments` 表**：

- 本机附件仓：`~/.nx-kv/attachments/local/`（根目录可由 `NX_KV_ATTACHMENTS` 覆盖），`storage='local'`。实现 `src/core/localatt.ts`。
- **不存在云端镜像**：v7 起全面本机化，没有云端图床、没有上传实现。`storage='cloud'` 只可能出现在 v2 迁移期留下的历史行（`migrations/v2-data.ts`），新写入一律 `local`。

**没有 `localatt` 表**——本机附件仓是文件系统，不是数据库表。写文档时别把 `localatt` 写成表名。

### 3.6 配置域

| 表 | 业务对象 | 主键 | 关键列 | 约束 |
|---|---|---|---|---|
| `templates` | **任务正文模板** | `id` | `category`(`newtask`/`delivery`/`enhance`/`context`)、`slot`(`prefix`/`suffix`/`tail`)、`body`、`vars_schema`（声明）、`vars`（值）、`is_default`、`enabled`、`sort_order`、`builtin`、`scope`（v3）、`origin_topic`（v3） | `ux_templates_default ON (category) WHERE is_default=1 AND deleted_at IS NULL`；`ix_templates_render ON (category, slot, sort_order) WHERE enabled=1 AND deleted_at IS NULL` |
| `settings` | 全局 k/v 设置 | `key` | `value`（**JSON 文本**）、`updated_at` | 无类型约束 |
| `meta` | 库自身元信息 | `key` | `value`、`updated_at` | `store_kind='sqlite'` 是唯一必需的键 |

`templates` 只承载**任务正文模板**（`newtask` 在用；`delivery`/`enhance`/`context` 是历史 seed 行，**不参与提示词渲染**）。提示词渲染走另一套——见 [[B04-提示词渲染链]]。

## 4. 软删除的两套语义（别混）

| 类别 | 表 | key/name 能否重用 | 唯一索引写法 |
|---|---|---|---|
| **身份型** | `repos` | **不可重用**（key 是跨机器导出的身份） | `UNIQUE` 不带 `deleted_at` 条件 |
| **实例型** | `topics` / `goals` / `templates` | 可重建（删掉再建同名是正常操作） | 唯一索引必须带 `WHERE deleted_at IS NULL` |
| **编号型** | `tasks` | `seq` 永不重用（历史引用不能漂） | `UNIQUE (topic_id, seq)` 不带条件 |

不实例型 / 不带条件的唯一索引，软删的行会永久占住名字——用户删完重建撞 UNIQUE 且无法自解。

## 5. 规范术语

新代码、新文档、新 UI 一律用「规范叫法」；历史别名只在读旧代码时参考。完整清单见 `docs/glossary.md` 第 5 节。

| 规范叫法 | 代码 / 表 | CLI | UI / 历史别名 | 必须避免 |
|---|---|---|---|---|
| **主题**（topic，本地队列） | `topics` | `localtask topic …` | 面板 page `dir` 显示「目录」；「队列」是功能同义词 | 不要把云端主题简写成「主题」；不要把「目录」当实体名 |
| **云端主题** | `modules/todo` 的 KV 主题 | `todo topic …` | 必须写全「云端主题」 | 与本地主题是两回事，key/编号不可互相套用 |
| **仓库** | `repos.type='repo'` | `repo …` | 面板仓库页 | 不要用「项目」指项目组 |
| **项目组** | `repos.type='group'` + `repo_group_members` | `board …`（**概念名是项目组，命令名沿用 board**） | 面板「项目组 / 分组」；「看板」是历史别名 | 代码/文档用 `group`；不要再造「仓库组」 |
| **参考仓库** | `repos` + `ext.ext_legacy_type='ref'`；`group_refs`；`repos.ext.ext_linked` | `repo --type ref …`、`repo bind …` | 面板「参考仓库」 | 不是 `refs`（文档）；DB `repos.type` 没有 `ref` 值 |
| **任务** | `tasks` | `localtask add/get/done/…` | 任务 | 别把 `tasks.id` 当对外编号，也别把 `seq` 当全局外键 |
| **文档** | `refs` / `ref_bindings` | `docs …` | UI「文档」 | 不要叫「参考文件」（与参考仓库混）；ref 是索引不是正文 |
| **任务模板** | `templates.category='newtask'` | `template …` | 设置页「任务模板」 | 不要用它改提示词渲染 |
| **工作空间**（cloud） | `config.groupId` | `group …` / `todo group` | 面板「工作空间」 | 不是项目组，也不是本地主题 |
| **附件** | `attachments` + `task_attach`/`ref_attach` + 本机附件仓 | `file …`、`docs attach` | 「附件 / 图片」 | 图片是 `kind='file'`；不要把 ref 当参考仓库 |

已知不统一（按规范写法纠正，不必顺手大改存量 UI）：主题在面板路由里叫 `dir`/「目录」；项目组在 CLI 叫 `board`、面板有「项目组 / 分组 / 看板」三种写法；云端工作空间与项目组都出现 `group`，必须靠上下文区分。

## 6. 数据层硬规则

1. **SQLite 是唯一业务数据源。** 不要引入 JSON 文件 / 原子 rename / 文件锁做业务数据；文件只存附件字节与文档正文。
2. **凡要出现在 `WHERE` / 排序 / 唯一约束里的东西，不许进 `ext` 或 `settings`**（无索引 / 无类型）。
3. **凭据绝不进库。** `token` / `baseUrl` / `email` / `userId` / `groupId` 只在 `config.json`。库会被 `VACUUM INTO` 备份、被 `db inspect` dump、被人拷走排障。
4. **新查询默认带 `deleted_at IS NULL`**；确需含软删行时在函数名/注释里写明。
5. **软删语义全链路统一**：不要一条路径软删、另一条硬删。
6. **多表/多行写入放同一个 `txw(...)`**；编号分配与插入同事务，避免并发撞唯一索引。
7. **行 ↔ 领域对象的映射集中在 `repo/rows.ts`**（例：`tasks.body` → JSON `text`、`from_src` → `from`）。
