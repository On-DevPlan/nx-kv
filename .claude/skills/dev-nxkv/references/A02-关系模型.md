# A02 · 关系模型：谁连谁、怎么连

> A 序列 · 底层数据结构之二。回答「这条边是什么语义、约束是什么、哪里容易连错」。
> 表与字段见 [[A01-数据模型]]；配置类键位见 [[A03-键与扩展位]]。

## 1. 全景图

```text
repos(key, type=repo|group)                        ← 一切归属的根
  ├─< repo_group_members(group_key,repo_key) >─ repos(key)
  ├─< group_refs(group_key,ref_key) >─────────── repos(key)   组级参考仓库（v4）
  ├─< topics.repo_key / topics.group_key
  │     topics(id, key=(cwd,group) 派生)
  │       ├─< tasks(topic_id, seq)
  │       │    ├─< task_links(src_id → dst_id)      派生链（历史，append-only）
  │       │    ├─< task_deps(task_id, dep_id)       编排依赖（当下约束）
  │       │    ├─< goals(task_id) ─< goal_checks(goal_id)
  │       │    └─< task_attach(task_id) ─< attachments(id)
  │       └─< topic_presence(topic_id)
  └─< ref_bindings(repo_key, group_key, ref_id) ─< refs(id)
                                                    └─< ref_attach(ref_id) ─< attachments(id)
```

不落在关系表里的「边」（落在 `ext` JSON 里，因为它们**不参与外键约束**）：

```text
tasks.ext.ext_deps_foreign        跨队列依赖，元素形如 "<topicKey>:<seq>"
topics.ext.ext_task_order          队列顺序（seq 数组），看板/列表的显示序
topics.ext.ext_workflow_state      工作流快照状态
topics.ext.ext_workflow_plugins    工作流插件状态
repos.ext.ext_linked               仓库级参考绑定（旧口径，v4 后与 group_refs 并存）
repos.ext.ext_getloop              项目级「持续 get」窗口配置
```

## 2. 关系逐条说明

### 2.1 仓库 ↔ 项目组（多对多）

`repo_group_members(group_key, repo_key)`。

- 两端都是 `repos.key`，组侧必须是 `type='group'`（跨表约束，CHECK 表达不了，**由写入层保证**）。
- `note` 挂在**关系**上，不挂在仓库上：「这个仓库在这个组里是干什么的」。它与 `ref_bindings.note`（「某份文档在这个列表里的一句话」）不是一回事，别混。
- `position` 是组内排序。
- 组删除 / 改名 → `ON DELETE CASCADE` / `ON UPDATE CASCADE` 自动跟随。

### 2.2 项目组 ↔ 参考仓库（多对多，v4 口径）

`group_refs(group_key, ref_key)`。

- 一个组 ↔ 多个参考仓库，一个参考仓库 ↔ 多个组。
- **组内所有仓库共享**，**没有继承 / 覆盖 / 排除**语义，也没有「仓库自己的参考仓库」。
- `note` 同样挂在关系上：「这条参考在本组里参考什么」。
- 与**仓库级绑定**（`repos.ext.ext_linked`，dev 侧 `kind='ref'`）**并列存在**，两类互不折算。v4 迁移把旧 `ext.ext_linked` 绑定搬进本表；**无归属组的绑定保留在 ext 里不搬**（不静默丢弃，`checkRefs` 会报「未迁移」）。

### 2.3 仓库 → 主题（1:N，可选组）

`topics.repo_key`（必填，`CASCADE`）+ `topics.group_key`（可空，`RESTRICT`）。

- 队列身份是 `(cwd, group)`：同一目录可以在多个组下各跑一摊活，各发自己的编号。
- 与 `repo_group_members` **不冲突，两层语义不同**：
  - `repo_group_members` = 这个仓库**可能**属于哪些组（成员关系，多对多）
  - `topics.group_key` = 这个目录**当下真的**按哪套上下文在跑（实例，每条一份编号）
- `group_key` 用 `RESTRICT`：置空会让该队列与「本目录单跑 repo」那条撞成同一个 `(cwd, NULL)`。

### 2.4 主题 → 任务（1:N）

`tasks.topic_id`（`CASCADE`），`UNIQUE (topic_id, seq)`。

- 一个任务只属于一个主题。
- 任务对外编号是 `tasks.seq`（`#12`）；`tasks.id` 只在仓储/外键/跨主题依赖里出现。
- `seq` 只增不减；软删任务仍占编号。

### 2.5 任务 → 任务：派生链（append-only 历史）

`task_links(src_id, dst_id, type)`，方向恒为 **新 → 旧**。

| type | 含义 |
|---|---|
| `comment` | 由某条评论派生（评论区划选 → 新任务）；`fork` 也复用这个 type |
| `reopen` | 重开：上一轮没通过，另起一条接着做 |
| `feedback` | 完成回调的反馈里提出了新活 |

三条口径：

1. **不存反向边**——「谁从我这儿派生」靠 `dst_id` 上的索引查。
2. **一个任务只有一个来源**（`ux_task_links_parent ON (src_id)`）⇒ 链是**树**不是网。但「整条创建链」递归查即可（`WITH RECURSIVE`），不必单独建表。
3. **不可变语义**：reopen 不就地改同一条（旧任务定格、派生新任务、两者用边连起来）。于是 id 永远指向当初那条内容，历史不会被后续轮次覆盖。

依附的是全局 `tasks.id`，不是 `(topic, seq)`——任务被搬到别的队列后链不会断（旧实现存 `"topicKey:id"` 字符串，搬队列就得重写字符串，漏一处就成虚链）。

### 2.6 任务 → 任务：编排依赖（可变约束）

`task_deps(task_id, dep_id)`，两列都是**全局 `tasks.id`**。

**为什么和 `task_links` 分成两张表**：两者生命周期正好相反。

| | 派生链 | 依赖 |
|---|---|---|
| 性质 | 发生过的事实 | 当下的约束 |
| 写操作 | append-only，永不改永不删（除级联清库） | 会加会撤 |
| 混成一张表的后果 | 「删掉一条依赖」和「删掉一段历史」变成同一种 DELETE，手滑就把追溯依据删了 |

写入 `task_deps` 时必须按 `(topic_id, seq)` **解析成全局 id 再写**。**禁止把 `seq` 直接写进 `dep_id`**——多队列下会指向别的任务。

跨队列依赖是另一条通道：落在 `tasks.ext.ext_deps_foreign`，元素形如 `"<topicKey>:<seq>"`（id 是**对方队列的 seq**）。它**不进本队列引擎节点图**，只在前置直查时生效，解析不到就 fail-open（不挡）。

### 2.7 任务 → 时间目标 → check

`goals(task_id)` → `goal_checks(goal_id)`。

- 目标挂在**任务**上，不挂队列——队列是容器，没有「交付」这件事。
- 一个任务一个目标（`ux_goals_task`）：任务是某一轮的工作单，一轮一个截止时刻。要加时间是改 `duration/deadline`；要重做是派生新任务、新任务自己的目标。
- `goal_checks` 里的 `elapsed_sec` / `remaining_sec` / `overtime_sec` 是**当时的快照**，只增不改：`deadline` 会被延期，不存快照的话历史 check 会被重算成另一个数。

### 2.8 仓库 / 组 ↔ 文档（列表式多对多）

`ref_bindings(repo_key, group_key, ref_id, type, position, note)`。

| `type` | 宿主 | `group_key` |
|---|---|---|
| `repo` | 仓库自己的描述列表 | 必须为空 |
| `group` | 项目组自己的描述列表 | 必须为空 |
| `group_repo` | 仓库在某个组里的单独列表 | 必须给出 |

- 没有「主引用」这种单值字段：**列表首项就是 `position` 最小的那一项**。
- 宿主用 `key` 而不是 id 引用：换机器重建关系时，key 是唯一还能对上的东西；`ON UPDATE CASCADE` 让改名不留下孤儿行。
- 同一宿主同一 ref 只出现一次（`ux_ref_bindings` 用 `COALESCE(group_key,'')`，因为 SQLite 里 NULL 在唯一索引中互不相等）。

### 2.9 任务 / 文档 ↔ 资源（三层结构）

这是最容易连错的一段，务必分清三层：

| 层 | 位置 | 语义 |
|---|---|---|
| 资源是什么、字节在哪 | `attachments` 行 | 真相 |
| 引用关系 | `task_attach` / `ref_attach` | 程序查的边 |
| 正文里的 `![名](fileId)` | `tasks.body` / 文档正文 | 给人和 agent 看的线索 |

三者不重复：改正文时同步一次绑定即可；正文被删但绑定还在 = 用户显式挂载的东西不会丢。

**role 是「边的语义」，不是资源的属性**：

| 关系表 | role | 含义 |
|---|---|---|
| `task_attach` | `inline` / `attach` / `doc` | 正文内嵌 / 显式挂载 / 作为文档资料挂载 |
| `ref_attach` | `inline` / `attach` / `reference` | 正文内嵌 / 显式挂载 / 正文里的内部资源链接（`nxkv://task|ref`） |

**role 优先级 `attach > doc > reference > inline`**（`src/core/attachmentdb/relations.ts` 的 `ROLE_PRIORITY`）：越「显式」越不容易被正文覆盖。正文同步不得把用户显式挂的东西降级；同 role 重复写只刷新 `position`。`note` 只在同 role 且调用方**显式给了**时才更新——正文同步不传 note，就不会冲掉用户写的说明。

`attachments.dedupe_key` 是「同一逻辑资源」的跨行去重键（软删后允许重新登记），唯一索引带 `WHERE dedupe_key <> '' AND deleted_at IS NULL`。

### 2.10 主题 ↔ 等待态

`topic_presence(topic_id)`。

放库里唯一的原因是**跨进程**：`wait` 进程与面板进程不共享内存，没有别的通道能把「我在等」传出去。单独成表而不是塞进 `topics`：瞬态与持久混在一行只能逐字段重置；独立表可以整表清空；进程被 SIGKILL 时残留只污染这张小表，不会让队列本身看起来像在等。

## 3. 四种关系语义（判边时先分类）

| 语义 | 例子 | 写操作 | 生命周期 |
|---|---|---|---|
| **归属**（外键 + 级联） | `tasks.topic_id`、`ref_bindings.ref_id` | 随宿主增删 | 与宿主同寿 |
| **历史**（append-only） | `task_links` | 只增 | 永久（除级联清库） |
| **约束**（可变） | `task_deps` | 可加可撤 | 与被约束对象同寿 |
| **实例**（瞬态） | `topic_presence` | 随时写 | 进程重启即清 |

判错语义 = 后面所有维护动作都错。**先问「这条边是发生过的事实，还是当下的约束？」**

## 4. 关系层的四个高频坑

| 坑 | 症状 | 正确做法 |
|---|---|---|
| 身份混用 | `dep_id` 存了 `seq`；CLI 显示 `tasks.id` | 外键一律全局 `tasks.id`，显示一律 `seq` |
| 唯一索引漏 `COALESCE` | 可空列上的唯一约束形同虚设（NULL 互不相等） | `COALESCE(group_key,'')` 包一层；实例型还要带 `WHERE deleted_at IS NULL` |
| 软删只做一半 | 删完重建撞 UNIQUE 且无法自解 | 全链路统一 `deleted_at IS NULL`；身份型 key 不重用、实例型可重建 |
| 派生与依赖混表 | 删依赖顺手删了历史链 | 分两张表，语义不同 |

## 5. 关系写入的唯一实现

- 附件资源与关系：**`src/core/attachmentdb.ts`**（对外入口）→ `attachmentdb/{ids,resources,relations,docs,query}.ts`。
  - `ids.ts`：id 公式 + 正文解析纯函数（`parseAttachmentRefs`）
  - `resources.ts`：资源行 upsert（`ensureAttachment` / `upsertFileAttachment` …）
  - `relations.ts`：关系边写入与**整组重写**（`linkAttachment` / `syncTaskAttachments` / `syncRefAttachments` / `unlinkAttachment` / `updateAttachmentNote`）
  - `docs.ts`：`refs` 行与整库重扫（`ensureDocRef` / `syncDocAttachmentIndex` …）
  - `query.ts`：查询与生命周期
  放 core 的原因：`localatt`/`attachstore`（字节存储）与 docs/localtask 仓储（关系）都要用它，放模块层会造成「核心存储依赖业务模块」的倒挂。
- 任务依赖与派生链：写在 `src/modules/localtask/repo/tasks.ts` 一带，**必须**经 `src/modules/localtask/writes.ts` 的 `withTopicMutator`（见 [[B05-依赖与工作流引擎]]）。
- 队列顺序、工作流状态、跨队列依赖：`topics.ext` JSON，由 `src/modules/localtask/repo/topics.ts` 读写。
