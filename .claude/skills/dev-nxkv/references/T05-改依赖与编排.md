# T05 · 改依赖 / 闸门 / 编排

> 任务之间的「谁等谁」由纯函数判定，落库只是数据。改判定必须能被单测钉住，
> 且**所有任务写入必须经过 `withTopicMutator`**（否则派生链会错）。

## ① 前置（先跑，拿事实）

```powershell
ls src/core/workflow/                                       # edges / readiness / lifecycle / layout / plugin-registry
grep -n "export function" src/core/workflow/readiness.ts     # parseDepRef / normalizeBlockBy / isReadyToClaim
grep -n "withTopicMutator" src/modules/localtask/writes.ts   # 唯一写入口
node bin/kv.mjs localtask chain --id <id> --json             # 任务链：origin/reopen/comment/current + 祖先
node bin/kv.mjs localtask list --json                        # ready / blockBy 现状
```

## ② 先判定：改的是哪一类

| 需求 | 载体 | 位置 |
|---|---|---|
| 任务 A 等任务 B 完成才能领 | `tasks.blockBy`（`DepRef`：本地或跨队列） | `readiness.ts` 的 `normalizeBlockBy` / `isReadyToClaim` |
| 工作流节点状态机（pending/ready/running/success/failed） | `workflow/lifecycle.ts` 的 `NODE_PHASES` | 状态迁移只能走 `lifecycle.ts` |
| 队列顺序 / 领取优先级 | `topics.ext` 的排序字段 | `localtask/repo/topics.ts` |
| 编排面板（dag 页）呈现 | `src/web/frontend/page/dag/` | 走 `T03` |

## ③ 动作

1. **判定逻辑写成纯函数**：入参 `(task, allTasks, opts)`，出参布尔/节点集合，不读 DB、不读全局。放在 `core/workflow/readiness.ts` 或同层新文件。
2. **写入必须经 `withTopicMutator`**：

```powershell
grep -n "withTopicMutator" -A 12 src/modules/localtask/writes.ts | head -20
```

所有改 `tasks` / `topics` 的路径都从它走——它负责派生字段、事件、快照同步。绕过它 = 派生链与事件流静默不一致。

3. **跨队列依赖**用 `{ kind: 'foreign', key, id }`，同队列用 `{ kind: 'local', id }`；`formatDepRef` / `parseDepRef` 是唯一序列化入口，别自己拼字符串。
4. **环检测**：加边前跑一次可达性检查（`edges.ts` 的 `successorsOf` 从新边终点回溯），自依赖直接拒绝。
5. 改状态语义 → 同步 `WORKFLOW_PHASES` / `NODE_PHASES` 与 `HOOK_CHAINS`，并检查面板 `dag` 的渲染分支。

## ④ 自检

```powershell
node --import tsx --test tests/unit/workflow-*.test.mjs
node --import tsx --test tests/unit/localtask-*.test.mjs
pnpm typecheck
node bin/kv.mjs localtask chain --id <id> --json      # 边真的落上了
node bin/kv.mjs localtask list --json                 # ready 与 blockBy 一致
```

| 检查 | 通过判据 |
|---|---|
| 自依赖 | 加 `blockBy` 指向自己 → 拒绝并给结构化错误 |
| 环 | A→B→A → 被拒，不产生半条边 |
| 跨队列 | `foreign` 只在对方完成后 ready |
| 派生一致 | 改完 `chain` 的祖先、`list` 的 `ready` 与库内一致 |
| 事件 | 依赖变化有对应事件（`core/workflow/event-names.ts`） |

## ⑤ 失败分支

| 症状 | 原因 | 处置 |
|---|---|---|
| 任务永远不 ready | `blockBy` 指向已取消/已删任务 | 加边时校验目标状态；删除时清边 |
| 任务「莫名其妙」ready | 绕过 `withTopicMutator` 直接写表 | 改回唯一入口 |
| 链上祖先看不全 | `chain` 只追 reopen 派生，不追 `blockBy` | 用 `edges.ts` 的 `edgesFromTasks` 自建图 |
| 跨队列依赖丢 | `key` 没规范化（大小写/分隔符） | 用 `parseDepRef` 统一 |
| 面板 dag 画错 | 前端自己算边 | 前端只渲染接口给的 edges |

## ⑥ 反模式

- 在 SQL 里写「完成则 ready」的判断（判定属于纯函数层）。
- 用 `tasks.id` 做对外寻址（对外是 `seq`；跨队列必须带 `key`）。
- 为了一次性需求往 `NODE_PHASES` 里加状态——状态机是全局语义，加之前先确认没有别的路径依赖它。
