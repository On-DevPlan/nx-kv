# A05 · 任务链成块 + 反馈识别 + 回写 topic 的 ref

## 这一篇解决什么

「这个项目 / 组下面有哪几条任务链」「每条链最新一轮到底定了什么」
「把这堆结论**回写成这个 topic 的 ref**（项目介绍 / 组介绍），让下一个人不用重跑一遍」。

## 一、先认 topic

一个 **topic** = 一个工作目录的任务队列（一个 repo、或 repo+group 定位出的那一个队列）。
「回写到 topic 的 ref」= 回写到**这个 topic 对应宿主**的文档：仓库的主篇 / 组的主篇 / 组内仓库篇。

## 二、把 topic 下的任务看成「多块链」

1. **看主题总览**：`nx-kv localtask list --json` → 每个主题一行：现状摘要、待领取数、是否等待中。
2. **看单条**：`nx-kv localtask show --id <n> --json`（正文 + 附件清单与本机路径）。
3. **看链**：`nx-kv localtask chain --id <n> --json` → 这条任务的历史节点
   （`origin` / `reopen` / `comment` / `current`）+ forkOf 祖先与子任务。
4. **面板上**（更快）：任务列表点开某条 → 右侧「任务链」视图可旁路看每一轮正文，不打断当前轮。

**链的形状**：

```text
origin ──reopen──▶ 下一轮（new id, pending）
   └──comment───▶ 评论派生（new id）
                    └──…──▶ current（链尖：当前该干的那条）
```

- `reopen` / `comment` / `fork` 都**派生新编号**的 pending 任务；旧任务定格（done 保持 done）。
- forkOf 是「从另一条复制出来」的副本（不继承时间目标与依赖）——它和 reopen 是两种不同的派生。

## 三、识别「最新更正与反馈」

每轮任务的正文里带着上一轮的**完成总结 callout** 与**验收反馈段**：

```markdown
> [!NOTE] 第 1 轮 · 完成总结
> …上一轮做了什么 / 关键决策…

> [!WARNING] 第 1 轮 · 验收反馈
> **用户的原话**
```

所以判定规则是：

| 要什么 | 看哪里 |
| --- | --- |
| **最新更正** | 链尖（`chain` 里 kind=`current` 的节点）那条任务正文的「完成总结 + 验收反馈」段，以及它自己的正文 |
| 历史结论 | 旧节点的完成总结（`roundSummary`）——**是历史，不是现状** |
| 用户到底要什么 | 验收反馈段里**用户的原话**（不要转述成自己的话） |
| 这条链还活着吗 | 链尖是 pending/claimed（还要干）还是 done（这轮完了） |

**别把旧轮的结论当现状写进 ref**——那是最常见的回写事故。

## 四、把结论回写成 topic 的 ref

1. **选宿主**（对应 topic 的三种落法）：
   - topic = 仓库 → 仓库**主篇**：`docs bind --repo`；
   - topic = 组 → 组**主篇**：`docs bind --board`；
   - 某仓库在组里的定位 → **组内仓库篇**：`docs note-bind --board --repo`。
2. **合成正文**（结构固定，五段）：

   ```markdown
   # <项目 / 组> · 现状

   ## 现在是什么样
   （已落地的东西：模块、命令、行为；写到能让人直接用）

   ## 关键路径
   （入口文件 / 函数、命令、配置项、验证方式——写全路径）

   ## 最近更正
   - 第 3 轮：<改了什么> —— <为什么>（来源：#131 验收反馈）
   - 第 2 轮：<改了什么> —— <为什么>

   ## 未决与遗留
   （还没做的、已知但没修的、依赖别人的）

   ## 下一步
   （谁可以接着做什么，从哪下手）
   ```

3. **写入**（长文用文件，别在命令行硬拼）：

   ```bash
   # 已有主篇：直接改正文（先 docs get 存一份旧版以便回滚）
   nx-kv docs get --ref ref:<refId> --json > 旧版.json
   nx-kv docs set --ref ref:<refId> --body-file ./现状.md --json

   # 还没有主篇：新建 → 写正文 → 绑成主篇
   nx-kv docs ref add --owner repo --repo <仓库key> --desc "<项目 / 组> · 现状" --json
   nx-kv docs set --ref ref:<新 refId> --body-file ./现状.md --json
   nx-kv docs bind --repo <仓库key> --ref ref:<新 refId> --json
   ```

4. **复核**：`nx-kv docs bindings --host <仓库key> --json`（主篇在那儿吗）
   与 `nx-kv docs get --ref ref:<refId> --json`（正文写进去了吗）。

## 五、偏差与陷阱

| 偏差 | 正确做法 |
| --- | --- |
| 把旧轮的完成总结当现状 | 现状只取**链尖**那条的结论；旧轮标成「最近更正」 |
| 把用户反馈转述成自己的话 | 反馈段引用**用户原话**（转述会丢掉真正的诉求） |
| 几十条链拼成一大段 | 一条链一段，段内标「第 N 轮」，段间留分隔 |
| 直接覆盖主篇不留旧版 | 先 `docs get` 存一份；回写是高频动作，得能退回去 |
| 新建一篇 ref 去「顶替」旧主篇 | 换主篇用 `docs bind --repo --ref <新>`（旧篇仍可查） |
| ref 只写「已完成」 | 必带「关键路径」：入口文件 + 命令 + 验证方式，否则下一个人还得重跑 |
| 组内仓库的结论写进组主篇 | 组内仓库定位用 `docs note-bind --board --repo` |
| 用 `localtask list` 的摘要当现状 | 那是面板顶栏的一句话摘要，不是结论；要结论看链尖正文 |
