# R02 · 需求 · 加或改一条命令 / 业务规则

> 命中信号：「加一个命令」「加个接口」「改 xx 的判定」「接口返回不对」「错误码不对」。
> 形状与事务规矩单点维护在 `P02-action形态与事务.md`（骨架照真实文件抄，不要抄本文）；
> 契约生成见 `P03-契约生成.md`；对外收口见 `R06-发版.md`。

## ① 前置（先跑，拿事实）

```powershell
node bin/kv.mjs routes --module <模块>                 # 现有入口，确认 cli 路径不重复
ls src/modules/<模块>/actions/                         # 命名与骨架
cat src/modules/<模块>/actions/<最相近的>.ts           # 照抄这一份
grep -n "^export" src/modules/<模块>/service.ts         # 业务函数有哪些
ls src/modules/<模块>/repo/                             # SQL 在哪些文件
grep -rn "<业务名词>" src/modules/<模块> --include=*.ts | head -20   # 这个判断现在出现在几处
ls tests/unit | grep "<模块>"                           # 已有用例（没有 = 这是新行为，要补）
```

## ② 判定

**加还是改**：

| 需求 | 走哪节 |
|---|---|
| 新能力、新入口，或给已有命令补可选参数 | §③（加入口；补参数 = 改原文件的入参声明，不复制第二条路径） |
| 行为算错、边界没判、错误码不对、派生字段不对 | §④（改实现） |
| 查出来的行不对、漏了 `deleted_at IS NULL`、排序不稳 | §④，改 `repo/*.ts` |

**改的东西属于哪个模块**（按业务对象，不按 UI 页面）：

| 改的东西属于 | 模块 |
|---|---|
| 仓库、项目组（`board`）、参考仓库 | `repos` |
| 任务、队列、领取/完成/重开/等待 | `localtask` |
| 文档（refs）、正文、绑定 | `docs` |
| 附件、mdfile、文件夹 | `file` |
| 任务模板、提示词模板 | `templates` |
| 全局设置 | `setting` |
| 库诊断、备份、迁移 | `db`（纯 CLI，`http: null`） |
| 内置技能安装/输出 | `bundled` |
| 时间目标 | `tasktool` |
| 平台级（bootstrap/health/routes/contract） | `system` |

## ③ 动作 · 加入口

**1. 建文件** `src/modules/<模块>/actions/<cli首词>-<动词>.ts`，按 `P02-action形态与事务.md`
§② 的骨架填（`id` 全局唯一、`cli` 必须有、`http` 可为 `null`、zod 契约内联、`run` 只编排）。

**2. 业务进 service，SQL 进 repo**：规矩（错误类型、事务、`withTopicMutator`、`nowMs`）
见 `P02-action形态与事务.md` §③，不重复展开。

**3. 生成清单与契约**：

```powershell
pnpm gen        # = gen:actions + gen:api；刷新 _manifest.generated.ts 与前端 typed client
pnpm gen:dart   # action 要对外（声明了 output）时才需要
```

**4. 立刻验证一次**（然后**重启 serve**——路由在进程启动时编译）：

```powershell
node bin/kv.mjs routes --module <模块>        # 新命令必须出现在输出里
node bin/kv.mjs <首词> <动词> --json          # 真跑一次，看返回形状
```

**5. 要面板入口** → `R04-加面板页面.md`；对外可见面（assets/README/CHANGELOG）→ `R06-发版.md`。

## ④ 动作 · 改行为

1. **定位唯一实现**，把重复的判断合并掉：

```powershell
grep -rn "<函数名>\|<判定关键词>" src/modules --include=*.ts | head -20
```

2. **改在 service 层，action 只编排**；错误语义与事务规矩见 `P02-action形态与事务.md` §③。
   判定逻辑若属「谁等谁」类纯函数，走 `R09-改编排闸门.md`。

3. **派生字段不手写**：DAG、`ready`、`blockBy` 的另一侧由 `writes.ts` 的派生函数维护
   （清单见 `P02-action形态与事务.md` §③）。

4. **补一条钉住行为的用例**（改行为却没改测试 = 没有回归防线）：

```powershell
node --import tsx --test tests/unit/<域>-<行为>.test.mjs
```

5. **同步注释与决策**：`service.ts` 顶部的「读写口径」注释如果与新行为不符，一并改；
   动了语义取舍就补 `docs/decisions/`。

## ⑤ 自检（全部通过才算完）

| 检查 | 命令 | 通过判据 |
|---|---|---|
| 注册成功 | `node bin/kv.mjs routes --module <模块>` | 新 cli 与 http 都在，无重复 |
| 类型 | `pnpm typecheck` | 退出码 0 |
| 契约 | `node --import tsx --test tests/unit/registry.test.mjs` | 通过（校验模块↔视图↔`/api` 字面量） |
| 行为 | 真跑一次 | 返回符合预期；边界值（空、0、已删除、跨队列）逐个走过 |
| 错误语义 | 非法输入 | 返回结构化错误码，不是 500 / 崩溃 |
| 唯一实现 | `grep` 复核 | 同一判断只存在一处 |
| 派生一致 | `node bin/kv.mjs localtask chain --id <id> --json` | `chain` 祖先、`list` 的 `ready` 与库内一致 |
| 回归 | 该域既有用例 | 全绿；新增行为有用例 |

## ⑥ 失败分支

| 症状 | 原因 | 处置 |
|---|---|---|
| 面板请求新接口 404 | serve 的路由在**进程启动时**加载 | 重启 `node bin/kv.mjs serve`（纯前端改动才只需刷新） |
| 前端调新接口类型报错 | 没跑 `pnpm gen` | 跑 `pnpm gen` 再 typecheck |
| 改了 service 但接口行为没变 | 另有第二条实现（action 里也写了一份） | `grep` 同一关键词，合并到 service |
| 任务永远不 ready | 判定读了已删除/已取消的行 | 判定前过滤终态；删除时同步清边 |
| 错误码从 400 变成 500 | 用了普通 `Error` | 换 `badInput` / `notFound` / `conflict` |
| 单测单独跑过、全量跑挂 | 用例之间共享了库或全局状态 | 用 `tests/support/test-store.mjs` 的临时库 |
| 界面数字与接口不一致 | 前端自己又算了一遍 | 判定只留后端，前端只渲染接口结果 |

（形状与事务层面的失败分支——命令重复、`.ts` 后缀、`tx` 抛 `TypeError`、绕过
`withTopicMutator`——见 `P02-action形态与事务.md` §⑤。）

## ⑦ 反模式（见到就改）

- 改行为先复制一条新路径，而不是在原文件改（同一判断出现两遍 = 下一次不一致的起点）。
- 在 action 层写业务分支（同一个判断出现在两条命令里，改一处漏一处）。
- 在 SQL 里写业务判断（「完成则 ready」这类属于纯函数层）。
- 改行为时顺手放宽约束来「让用例过」。
