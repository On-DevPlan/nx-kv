# 场景：领任务 · 确认意图 · 再解决

> 归属主文档 [[nx-kv]]。当你是**本机任务队列的消费端**——提交方（用户或另一个
> 工作目录的 agent）把任务投到按「cwd + 项目组」派生的主题里，你负责领任务、
> 对齐意图、做完回填——读本文件。

关键在中间那几步「确认」：**不确认不动手**。任务往往模糊、多条、或覆盖多个主题，
先对齐能避免大段返工。

## 何时进入

- 用户让你「领取 / 看一下 / 处理」本目录（或某个主题）的任务
- 用户提到「发布的任务」「任务队列」「待办」「队列里的活」
- 你被另一个目录的 agent 委托了任务，需要消费
- 用户要求「先确认意图再执行」「把任务聚类成文档」

不确定是否该进入时，**倾向进入**——这比跳过确认直接开干安全得多。

## 两条行为准则（必读，覆盖全流程）

> 遇到相应场景**主动先问用户**再行动，不要沉默地自行处理。

### 1. 清理 / 覆盖上下文时，先问用户

删除、改写、合并、丢弃任何上下文信息（任务文本、主题提示词、之前的状态、用户给的背景）
之前，主动向用户确认：**是要丢弃、改写还是补充？**

沉默的清理 = 信息丢失 + 用户不知情。

### 2. 先自己查到底，摸不到底再问

拿到需求 → **先别问、自己去摸** → 摸不到底再问。

**第一步：在当前目录穷尽调查。** 翻代码、读文档、读配置、查 git 历史、看相关任务、
跑命令验证、读测试、用 grep/find 搜。

- 当前目录**能回答的，不许问用户**
- 不许「凭常识猜默认值」「还没查就先问」「查到一半就问」、把能查到的推给用户

**第二步：确实超出当前目录能力，才问用户。** 确认无法解决后，告诉用户
「**我已经查过 X、Y、Z，缺的是 W，请提供**」——把已查证据一起摆出来。

真的需要外部资源的：配置项 / 凭据 / 外部 prompt / 别的项目文件 / 用户主观偏好 / 业务决策。

> 反例：任务说「线上如何访问」，直接问「线上地址是？」。正确做法是先看 `deploy.yml` /
> `docker-compose` / `README` / `docs`，能推断就推断，推断不出再问并摆已查证据。

## 前置依赖

- **动手前必须调用** `superpowers:writing-plans`
- 时机：**Step 7 确认主题意图之后、Step 8 开始解决之前**
- 把已确认的意图作为 spec 交给它，产出实现计划（计划存放到哪、怎么命名，由它自己的规范决定），**按计划**再解决
- 任务拆分、写法、执行交接都以 `superpowers:writing-plans` 为准，本文件不重复

## 核心流程（8 步）

```mermaid
flowchart LR
  A[1 确认主题] --> B[2 看该主题待领取]
  B --> C[3 读 instruction / 文档]
  C --> D[4 不立即执行 → 摆给用户确认/补充]
  D --> E{多条任务?}
  E -- 是 --> F[5 按主题聚类]
  F --> G[6 生成意图文档]
  G --> H[7 确认主题意图 + writing-plans]
  E -- 否 --> H
  H --> I[8 领取 / 解决 / done 回填]
```

### Step 1 — 先确认主题

```bash
nx-kv localtask list --json
# → { topics:[{ key, name, dir, waiting, pending, ... }], waiting }
```

主题由「完整当前目录 + 项目组」派生；不在本目录时用 `--cwd` 指过去。
**先确认看的是不是你要的那个目录**——看错目录会「什么都查不到」，
而那不是「没有任务」，是「看错地方了」。

### Step 2 — 一次看全该主题的待领取

```bash
nx-kv localtask list --json        # 找到自己的 topic，看 tasks[] 里的 pending
nx-kv localtask show --id <n> --json   # 逐条看正文与状态（只读，不领取）
```

**不要直接 `get` 连发**：`get` 是**领取**动词（会改状态、起计时）。
要先对齐意图时用 `show` / `preview`；只有确定要开干时才 `get`。

### Step 3 — 读上下文

**探索整个项目时派一个 subagent 收集上下文**，比你自己逐个文件翻更省上下文：

- 读任务正文 + 面板/CLI 的 `instruction`（项目组上下文、附件、时间目标、ack 要求）
- 需要读文档时：`nx-kv docs get --ref <refId> --json`（仓库主篇通常已内嵌在 instruction 里，
  其余只给 refId + desc，**按需取**）
- 读任务文本，把含糊措辞、缺的信息、明显的错误标出来
- 把每条任务**改写成清晰的表述**（可执行、有边界、可验收），但**不改原意**
- 可选：让 subagent 一并返回相关的、可作为依据的 skill 条目

### Step 4 — 不要立即执行，先摆给用户确认

拿到任务**先停下来**。直接开干是这里最常见的错误。

把润色后的任务清单摆给用户：

- 每条确认「你理解得对不对」
- 让用户补充缺失的背景、约束、优先级
- 合并 / 删除过时任务在这里一并敲定

### Step 5 — 按主题聚类

若有多条任务，按**主题**聚类（如「CLI 重构」「测试补全」「文档」各成一簇）。
一条任务只属一簇，簇名即主题意图。

### Step 6 — 生成意图文档

把聚类结果写成结构化文档，落到**当前项目**的文档目录（如 `docs/<主题>-意图.md`；
项目已有设计文档 / spec 目录就放那里）：

- 每个主题：任务列表、目标、上下文/提示词摘要、边界、验收标准
- 文档既是 Step 7 确认的载体，也是后续执行的依据

### Step 7 — 确认主题意图 → 交给 writing-plans

把文档 / 聚类结果交给用户确认每个主题的意图与优先级。**用户拍板后才算对齐。**

对齐后**立即调用 `superpowers:writing-plans`**，把已确认的意图作为 spec 产出实现计划。
计划落地后才进 Step 8。

### Step 8 — 按计划解决 → **完成即回填 `localtask done`**

确定开干后先**领取**（`get` 会改状态；带时间目标的任务领取即起表）：

```bash
nx-kv localtask get --json
# → { status:"ok", task:{ id, text }, instruction:"…" }
```

按主题逐簇解决。**每解决完一条，立即回填**——这是收单闭环的最后一步，
漏掉会让任务一直挂在待领取队列：

```bash
nx-kv localtask done --id <n> --summary "改了什么 / 怎么验证 / 遗留问题"
```

- 用 Step 8 拿到的 `task.id` 定位（**主题内唯一**，不要用正文内容当 key）
- `--summary` 写清楚，供下一轮 agent 与面板查看
- 同主题多条任务**逐条解决、逐条回填**，不要攒到最后一次填
- 用户看完结果提修改意见 → `nx-kv localtask reopen --id <n> --text "<新正文>"`（同号重开）

做完这一轮、进入守候时：

```bash
nx-kv localtask wait --timeout 180 --json   # 本轮最后一步；timeout 是业务结果
```

## 稳定契约（可依赖）

| 契约 | 内容 |
| --- | --- |
| `--json` | 单个 JSON 值到 stdout；无多余文本 |
| 退出码 | `0` 成功；`1` 失败（含参数/定位错误） |
| 错误码 | `code` 可取 `INVALID_INPUT` / `NOT_FOUND` / `CONFLICT` / `EXTERNAL`，优先用它分支 |
| 错误文本 | 含「不存在」「用法:」「已被领取」等稳定锚点，可作兜底判断 |
| 幂等 | 重复 `localtask topic add`、删除不存在的主题都不报错 |
| 状态冲突 | 已完成再 `done`、别人已领取再 `get` → `CONFLICT` + exit 1；语义是「已经是你要的」，跳过即可 |
| 纯本机 | 所有命令不触网、不需要登录 |

**一次拿齐上下文**：`nx-kv bootstrap --json` 返回版本与本机命令表，省去多次往返。

## 安全边界

- **不要**往别的主题写任务来「提醒自己」——那是污染别人的队列；要委托用 `kv-submit` skill
- **不要**在没有确认的情况下批量删除别人的任务
- 软删除可恢复：`localtask task restore --id <n>`；`topic remove` 默认拒绝删有未领取任务的主题
- 改正文、reopen 前先确认：用户是要**改写、补充还是丢弃**旧内容

## 避坑

| 坑 | 后果 | 正确做法 |
| --- | --- | --- |
| 直接动手不先确认意图 | 任务文本常是半句话，盲目执行必返工 | 走 Step 4：润色 → 摆给用户 → 用户补充 |
| 用 `get` 当「查看」 | get 是领取：改状态、带时间目标还会起表 | 查看用 `show` / `preview`，确定开干才 `get` |
| 解决完不回填 `done` | 任务一直挂待领取，队列失真、提交方不知完成 | 解决一条立即回填，`--summary` 写明结果 |
| 同一条任务连续 attach 用正文定位 | 正文被改写，定位漂移 | 一律用 `--id <n>` 定位 |
| 带时间目标提前 `done` | 返回 `blocked`，不会完成 | 按 hint 派 sub agent 重提需求，到点再 done |
| 把 wait 当失败重试 | timeout 是正常业务结果（exit 0） | 按「暂时没活」收尾，不要立刻重跑 |
| 沉默清理上下文（丢弃/改写/合并任务文本、prompt、用户背景而不告知） | 信息丢失、用户不知情、难以回滚 | 删除或改写前先问：丢弃 / 改写 / 补充？ |
| 需要外部资源就直接问（或凭「常识」猜默认值） | 下游全错、用户反复回答、推进变慢 | 先在当前目录穷尽调查，超出能力再问，且必须带「我已查过哪里、缺什么」 |
