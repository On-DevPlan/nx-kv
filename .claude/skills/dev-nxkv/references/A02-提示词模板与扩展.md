# A02 · SOP · 提示词模板体系与扩展（领取 → 讲透 → 规范扩展 → 检查点）

> 命中信号：交付给 agent 的提示词不对（少了一段 / 变量渲染成空 / 文案不像你要的）/
> 要给 agent **多一条上下文知识**（流程规则、必须遵守的约束）/
> 要在设置面板里改模板 / 要加一个新模板区块。
>
> 本篇是「提示词模板体系」的**唯一入口**：先把整套东西怎么转起来讲透，
> 再给**规范的扩展方法**（三种动作，各有落点与步骤）与**每一步的检查点**。
> 区块 / 变量 / helper 的速查表在 `B03-提示词模板与上下文.md`。
>
> 体系自 S0–S4 起是「插件制」：**一段 = 一个 PromptPlugin 类**，模板正文是数据（DB），
> 顺序是数组（唯一真相）。旧的 `BLOCK_DEFS` 静态表 / `composeSystemBlocks` / 前端手写参数表已删除。

## ① 前置：先把现场看清楚

```bash
node bin/kv.mjs localtask get --cwd "<项目目录>"                    # 领一条（无活时阻塞到超时）
node bin/kv.mjs localtask get --cwd "<项目目录>" --timeout 60       # 阻塞上限（**秒**；缺省用项目配置）
node bin/kv.mjs localtask get --cwd "<项目目录>" --param k=v       # 外部参数进 ctx（{{k}} / {{params.k}}）
node bin/kv.mjs localtask preview --id <id>                        # 零副作用：看这条会交付什么
node bin/kv.mjs localtask show --id <id> --cwd "<项目目录>"        # 任务本体 + 附件清单与本地路径
```

`get` 的三个关键点：

| 点 | 说明 |
|---|---|
| **默认输出就是交付原文** | 读原文别用 `--json`（那是给程序用的形状，不是逐字原文） |
| **拿到就要按段落执行** | 交付里的 `ack` 段写明「完成后必须调用 `localtask done --id <id> --summary "…"`」 |
| **阻塞 ≠ sleep** | `--timeout N`（秒）是服务端挂住请求到点返回 timeout，不是让你自己等 |

## ② 领取并读懂交付

交付是**几段拼起来的 XML 块**（默认 `XML 标签` 模式；也可切成「纯文本直追加」）：

| 段（标签） | 内容 | 什么时候有 |
|---|---|---|
| `<nx-kv.context>` | 仓库 / 组 / 参考仓库 / 其余组 | 登记了仓库就有（组材料只进**组任务**：正文 frontmatter 带 board） |
| `<nx-kv.attachment>` | 附件清单 + 取用方式 + 文档原文 | 任务带附件时 |
| `<nx-kv.timecheck>` | 时间目标检查指令 | 带时间目标时 |
| `<nx-kv.goalhint>` | 时间目标的可算上下文 | 带时间目标时 |
| `<nx-kv.doneguard>` | 未到点不许 done 的拦截文案 | 只在 done 被拦截时出现 |
| `<nx-kv.ext>` | 同主题还有多少待领取 | 队列非空时 |
| `<nx-kv.ack>` | 完成回填指令 | 总有 |
| `<nx-kv.getloop>` | 持续 get 指令 | 项目开了持续 get |

读的时候：先看 `ack`（怎么交差）→ 再看 `doneguard` / `timecheck`（有没有时间门禁）→
再看 `context`（这个仓库/组是什么）→ 有附件先按附件段的「取用方式」读
（图片看图、md 读正文、**文件夹先列目录**再读里面的文件）→ 然后才动手。

## ③ 动作 · 体系总览：一条交付提示词是怎么转出来的（五个部件各管一段）

```
① 取数        service / repo / docs / repos → 各插件的 data()
② 合并 ctx    compose() 按顺序 Object.assign 各插件 get('data')
              （ctx 只放**数据**；成文措辞不在这里）
③ 选模板      每段取「当前生效的那条」：lt.blockTemplates[segId].active
④ 渲染        compose()：按 orderIds 逐段 renderInstruction（模板 trim 为空 → 该段不出）
⑤ 包标签      XML 块（默认）/ 纯文本（appendMode 全局一个开关）
```

**五个部件，各管一段**：

| 部件 | 位置 | 谁改 | 关键规则 |
|---|---|---|---|
| 段落（插件） | `src/modules/promptplug/plugins/*.ts` 的类（`id` / `order` / `tag` / `label` / `dataSchema`） | 改代码 | `id` = 区块 id；`tag` = `nx-kv.<id>`；`order` 只是**播种默认位** |
| 顺序 | settings 的 `prompt.pluginOrder` 数组（运行期 order 位 = 下标 × 10） | 用户在设置面板拖动 / `PUT /api/prompt/order` | **数组是唯一真相**；不是插件类的 `order` 字段 |
| 模板条目 | settings 表的 `lt.blockTemplates`（每段 `{active, list}`） | 用户在设置面板改 | 内置条目**恒在且不可删改**；`active` 指向生效项 |
| 出厂模板 | `src/modules/promptplug/Template/blockTemplates.json` | 改代码 + bump `BUNDLE_VERSION` | 首启落库走 `ensure.ts`；升级**只刷内置文本**，用户条目与 active 不动 |
| 渲染 | `src/modules/promptplug/compose.ts` 的 `compose()` | 改代码 | **运行期不兜底**：`data()` / 渲染抛错 = 整次交付失败（模板在保存期已校验） |
| 引擎 | `src/core/instruction-template.ts` | 改代码 | `{{#if}}` / `{{#each}}` + 25 个 helper；保存期 `validateTemplate` 拒旧语法 |
| 设置面板 | `src/web/frontend/page/settings/prompt-templates-section.tsx` | 改代码 | 区块切换 → 模板列表 → 正文 → 「可使用参数」（由 `prompt.registry` 的 `fields` 派生） |

> 模板是**运行时数据**（用户在面板改），`dataSchema` 是**代码契约**——两者会漂移，
> 所以扩展必须同时动两边（见 §④）。

## ④ 动作 · 规范扩展方法：三种动作（加变量 / 加段落 / 加模板条目）

先判定要做哪一种：

| 你要做的事 | 动作 | 落点 |
|---|---|---|
| 已有段落里多给 agent 一个信息 | **扩展 1**：给插件加变量 | `dataSchema` + `data()` + 出厂模板 |
| 交付里多一段（新维度：规则、清单、提示） | **扩展 2**：加新插件 | 新类 + 注册 + 出厂模板 + 顺序播种 + 说明书 |
| 只是想改某段的**说法**（文案风格、多加一句） | **扩展 3**：加一条模板条目 | 设置面板：复制内置 → 改 → 启用 |

### 扩展 1 · 给已有段落加一个变量

| 步 | 落点 | 做什么 | 检查点 |
|---|---|---|---|
| 1 | 对应插件类的 `dataSchema`（`plugins/context.ts` 等） | 声明字段（`z.strictObject`；可选字段用 `.optional()`） | 严格对象：多写的键会被 `get('data')` 的 safeParse 拒 |
| 2 | 同一个类的 `data()` | 取数并投影成**纯数据**字段 | 字段名与业务词一致（`repo.introRefId`，不是 `repo.intro_id`） |
| 3 | 需要写回 ctx 才加 `writes` | 默认 `writes = []`（只读段不回写） | 只读段不参与 ctx 合并，但仍可读 seed |
| 4 | `Template/blockTemplates.json` 里该段的 builtin 正文 | 加占位 `{{新字段}}`（必要时 `{{#if}}` 闸门） | **空数据时整段不出现**，不能印空标签；改完 bump `BUNDLE_VERSION` |
| 5 | 内置 skill（`assets/nx-kv/references/`） | 写给 agent 的用法（什么时候用这个变量） | agent 看得懂这条信息是干嘛的 |

> 前端**不需要登记**：设置页「可使用参数」由 `GET /api/prompt/registry` 的 `fields`
> （`schema-bridge` 从 `dataSchema` 派生）直接渲染，没有第二份手写表（旧的
> `page/settings/prompt-template-params.ts` 已随 S3 删除）。

### 扩展 2 · 加一个新区块（新增插件）

| 步 | 落点 | 做什么 | 检查点 |
|---|---|---|---|
| 1 | `src/modules/promptplug/plugins/` 新建类，继承 `PromptPlugin` | 写 `id`（= 区块 id）/ `order`（播种位，留 10 的整数倍）/ `tag`（`nx-kv.<id>`）/ `label` / `dataSchema` / `data()` | `dataSchema` 必须 `z.strictObject`；`order` 漏写 tsc 直接报 TS2515 |
| 2 | `src/modules/promptplug/factory.ts` 的 `PLUGIN_IDS` + `buildDeliveryPlugins` | 把新类登记进装配 | `id` 唯一；`PLUGIN_IDS` 与 `shared/prompt-blocks.ts` 的 `PROMPT_BLOCK_IDS` 必须同序（有单测对账） |
| 3 | `Template/blockTemplates.json` | 加该段的内置条目（`{active:'builtin', list:[{id:'builtin', builtin:true, ...}]}`），并 bump `BUNDLE_VERSION` | 首启/升级由 `ensure.ts` 落库 |
| 4 | 顺序数组 | 新 id 不在存量 `prompt.pluginOrder` 里 → `resolveOrderIds` 会按 `order` 补位（不破坏已存顺序） | 老用户库里不需要手工迁移 |
| 5 | 内置 skill | 告诉 agent 这段是干什么的 | — |

> 设置面板**不需要额外登记**（左轨/卡片遍历注册表生成的），顺序拖动直接生效。

### 扩展 3 · 加一条模板条目（改说法）

1. 设置面板 →「提示词模板」→ 选中段落 → **复制**（内置条目不可改，复制出来才能改）；
2. 改正文 → **保存**（保存即落库，`validateTemplate` 会拒旧语法 / 语法错）；
3. **启用**（`active` 指向它）——不启用就只是躺在列表里；
4. 出问题想退回 → 段落上的「**恢复内置**」。

> 模板是**每用户的数据**（settings 表 `lt.blockTemplates`），不是代码；
> 改代码里的 `blockTemplates.json` **不会**覆盖用户已启用/复制的那条（升级只刷 builtin 文本）。

## ⑤ 检查点清单（扩展完必过，逐条有判据）

| # | 检查点 | 判据 | 怎么验 |
|---|---|---|---|
| 1 | **模板语法** | 保存不报错；没有旧语法（`{{#section}}` / `{{^x}}`） | 面板保存成功；`validateTemplate` 通过 |
| 2 | **变量解析** | 新占位符渲染出**真实内容**，不是空串 | `localtask preview --id <id>` 目视（**变量名写错不会报错，只会静默变空**） |
| 3 | **空数据闸门** | 数据为空时该段**整段不出现** | `preview` 一条没有该数据的任务 |
| 4 | **老交付没坏** | 原有各段的输出与改动前**逐字一致** | 改动前后各跑一次 `preview` 对比；或跑 `tests/unit/prompt-golden.test.mjs` |
| 5 | **顺序与双真相对齐** | `PLUGIN_IDS` 与 `PROMPT_BLOCK_IDS` 同序；`resolveOrderIds` 对缺 id 能补位 | `pnpm test:unit`（`prompt-blocks` / `prompt-order-render` 两条） |
| 6 | **参数表同步（自动）** | 设置页「可使用参数」能查到新变量 | 打开设置页看；`prompt-registry` 单测覆盖形态 |
| 7 | **门禁** | lint / typecheck / 单测全绿 | `pnpm lint`、`pnpm typecheck`、`pnpm test:unit` |
| 8 | **说明书** | 内置 skill 写清了新字段/新段落的用法 | 人工过一遍 |

> 第 2、3 条是**目前唯一能发现变量写错**的手段（Handlebars 未知变量渲染成空串，不报错）——
> 所以 `preview` 不是可选项，是扩展的必过关口。

## ⑥ 现状体检：这套东西现在的约束（S4 后）

| 事实 | 位置 | 含义 |
|---|---|---|
| 运行期**不兜底** | `compose()` + `assertPluginList` | 坏模板/空模板在保存期就拒；运行期抛错 = 整单失败。**故意**如此：静默回落会让「少半段」无人知晓 |
| ctx 仍有一处共享聚合 | `plugins/context.ts` 的 `deliveryCtxOf`（S1 从 `delivery-template.ts` 整体搬入） | 仓库/组投影集中在这里；其余段各在自己类的 `data()` |
| 变量知识只有一份 | 各插件 `dataSchema` → `registry.fields` | 前端速查表、CLI/HTTP 输入校验、模板白名单同源 |
| 顺序是数组不是常量 | `prompt.pluginOrder` + `resolveOrderIds` | 拖动排序即改真相；插件类的 `order` 只播种一次 |
| 模板正文只有一份 | `Template/blockTemplates.json` + DB 行 | 代码里没有 `DEFAULT_*` 模板常量（`DEFAULT_ACK_PROMPT` 等运行期缺省文本在各自消费方文件，有单测逐字对账） |

## ⑦ 自检

```bash
node bin/kv.mjs localtask preview --id <id>      # 零副作用看渲染结果：分段 + 告警
node bin/kv.mjs localtask get --cwd "<项目目录>"  # 真领一次，看最终交付原文
pnpm lint && pnpm typecheck && pnpm test:unit
```

| 检查 | 通过判据 |
|---|---|
| 领取流程 | 交付里段齐全、顺序符合 `prompt.pluginOrder`；`ack` 段要求回填 |
| 扩展生效 | 新段/新变量在 `preview` 里出现且**有内容** |
| 老交付一致 | 改动前后 `preview` 的原有段逐字相同 |
| 坏模板 | 保存期被拒（不是运行期回落）；`preview` 会直接抛错 |
| 门禁 | lint / typecheck / 单测全绿 |

## ⑧ 失败分支

| 症状 | 原因 | 处置 |
|---|---|---|
| 新变量渲染成空 | 变量名写错 / `data()` 没投影 / 挂在别的段下 | 按 §⑥ 的表核对投影位置；`preview` 看渲染结果 |
| 交付里出现空标签（`组定位：`） | ctx 字段存在但内容为空 | 给默认文案，或用 `{{#if}}` 整段闸掉 |
| 设置面板改模板没生效 | 复制/新建后**没启用**（`active` 仍指向内置） | 面板里点「启用」；或「恢复内置」回退 |
| 改了 `blockTemplates.json`，用户那边没变 | 升级只刷 builtin 文本且要 bump `BUNDLE_VERSION`；用户启用的是自己那条 | bump 版本号；面板里恢复内置 / 改用户那条 |
| 模板存不进去 | 旧语法或语法错；或生效模板被清空 | `validateTemplate` 的中文提示就是原因；空模板会被拒保存 |
| **领取整单失败** | 设计如此：`data()` 抛错 / 渲染抛错不回落 | 看报错里的段落 id 与 zod issues（`<id>: data() 返回与 schema 不符——…`） |
| 新段落在面板上看不到 | 没登记进 `PLUGIN_IDS` / 工厂装配 | 补登记（还有 `PROMPT_BLOCK_IDS` 对齐单测） |
| 拖动排序没生效 | `PUT /api/prompt/order` 被 `assertOrder` 拒（不是全部 id 各一次） | 看返回错误；面板会回滚并重读注册表 |

## ⑨ 反模式

- 在 ctx 里塞**成文措辞**（ctx 只放数据；措辞在模板里，用户才能改）。
- 在代码里再加一份模板常量（第二份真相；正文只放 `blockTemplates.json`）。
- 新增字段不 `preview` 就提交（变量写错不报错，只会静默变空）。
- 用 `try/catch` 给渲染加回落（S1 明确删除：静默降级比失败更贵）。
- 把「每轮都要说的规则」塞进任务正文（正文会被重排，规则会沉底）。
- 把「一次性要求」塞进全局模板（所有任务都被污染）。
- 改 settings 里的运行时数据来「修」代码 bug（那是用户数据，不是代码）。
- 为了让某段出现，去改**别的**段落模板（段各有职责，串味了没人查得出来）。
- 给 `prompt.pluginOrder` 手写数字（顺序靠数组下标；插件类的 `order` 只播种一次）。
