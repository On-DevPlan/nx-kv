# sessiontask-workflow — 阻塞等待用户回填任务的完整 SOP

> 归属 [[kv-sessiontask]]。当你要在一个对话里**不结束本轮**、靠一个阻塞工具
> 调用等用户在浏览器里继续回填任务时，按本 SOP 走。

## 一、端到端时序

```
1. agent 正常干活（分析、读写文件、调用其它工具）。
2. 当前任务做完、提交阶段结果，需要用户给下一条时：
     → 把「nx-kv sessiontask wait --summary "<当前现状总结>" --json」
       作为本轮【最后一个动作】调用；工具调用超时设为 120000 ms。
3. wait 的行为：
     a. 若该现状的等待点已有用户提前排队的 pending → 立即取走、不开窗、不阻塞；
     b. 否则在本机临时起一个 http 服务器（127.0.0.1，随机端口），
        自动打开浏览器弹窗，然后阻塞。
4. 用户在弹窗/面板看清现状，回填新任务 → 提交（Enter 或按钮）。
5. wait 解除阻塞，stdout(--json) 返回 {status:"ok", task}，进程退出。
6. agent 从工具结果读 task.text，继续干活、提交结果；做完回到第 2 步——循环。
7. 若 120 秒内没有回填：wait 返回 {status:"timeout"}（exit 0），
   agent 不再等待，收尾并结束本轮。
```

关键点：**第 2 步之后、工具结果回来之前，agent 不产生任何其它动作。** 用户的
回填正是通过这个工具结果进入对话的，等于用工具调用替代了在原始输入框打字，
agent 这一轮不会因为「等输入」而提前结束。

## 二、现状总结就是 key（怎么写）

wait 必带一句当前现状总结，它被归一化（折叠首尾/连续空白）后哈希成等待点 key：

- **回到同一个现状 → 用同一句总结（逐字一致）**，复用同一个等待点；首尾空格、
  连续空格的差异会被忽略，不影响 key。
- **进入新的现状 → 换一句新总结**，自然形成新的等待点。
- 总结要让用户**不读整段对话也能快速了解现状**，建议包含三要素：
  1. 已经做到哪一步 / 产出了什么；
  2. 当前卡在哪、有哪些可选项；
  3. 具体等用户决定或补充什么。
- 一句话为宜，≤200 字。示例：
  - `已完成登录，等待选择工作空间`
  - `已生成 3 个方案（A/B/C），等待你选一个再细化`
  - `面板已能提交，但删除还没接，等待确认是否现在补`

展示给用户的始终是现状原文；key 只是内部标识，agent 不需要自己算 key。

## 三、排队语义（用户可以提前投递）

- 用户在弹窗、常驻面板「实时任务」页或用 `sessiontask add` 提前提交的回填，会
  以 `pending` 进入对应现状的等待点。
- wait 总是取走该等待点**最早的一条 pending**，标记为已领取（consumed）后返回。
- 所以：
  - 等待点非空 → wait 立刻返回（`queued:true`），连弹窗都不打开；
  - 等待点为空 → 才开窗阻塞（`delivered:true`）。
- 已领取的任务保留为历史（状态「已领取」），不会被二次取走。

这让「用户趁 agent 还在忙，先把后面几条排好」成为可能：agent 每次 wait 都能
立刻拿到下一条，不打断节奏。

## 四、返回形状与退出码

成功（exit 0）：

```json
{
  "status": "ok",
  "key": "3f9a2c1d7e8b4a10",
  "summary": "已完成登录，等待选择工作空间",
  "task": { "id": 3, "text": "选择工作空间 A", "status": "consumed",
            "createdAt": "2026-10-06 10:00:00", "consumedAt": "2026-10-06 10:00:04" },
  "delivered": true,
  "queued": false
}
```

- `delivered:true` = 实时回填；`queued:true` = 取到提前排队的任务（二者互斥）。
- **任务内容永远读 `task.text`**，多行换行原样保留。

超时（exit 0，业务结果而非错误）：

```json
{ "status": "timeout", "key": "3f9a2c1d7e8b4a10",
  "summary": "已完成登录，等待选择工作空间", "timeoutMs": 120000 }
```

- 超时**不是失败**：退出码 0，按「用户没继续」收尾，不要按错误处理。
- 参数非法（如缺 `--summary`、缺 `--id`）才是错误（exit 1，文本带「用法」），
  按宿主失败流程处理。

## 五、弹窗任务表怎么用（可转述给用户）

- 顶部「当前现状」直接显示 agent 传入的现状总结，先看这句再决定回填什么。
- 大输入框：回填下一条任务；**Enter 提交，Shift+Enter 换行**。
- 状态栏倒计时显示还会等多久；归零未回填则本轮自动结束。
- 下方是该现状的任务表，状态分「待领取 / 已领取」，可删除。
- 提交后显示「已回填给 agent，正在返回」即说明 wait 已取走、窗口可关闭；agent
  做完会再开下一个弹窗。

## 六、分散答复：多个等待点并存

- 不同现状总结 → 不同等待点。常驻面板「等待点总览」把它们并排展示，每张卡显示
  现状、等待状态/倒计时、待领取数。
- 用户点选任一等待点即可**分别回填**，也可给多个等待点提前排队——答复被分散到
  各现状下，而不是挤在一个队列。
- agent 用对应现状调 wait 时只取该等待点的任务，互不串。

## 七、删除主题与批量删除

主题（工作目录）可整体删除，不必逐条删任务：

- **单个删除**：
  - 面板：主题卡片右下角「删除主题」；
  - CLI：`nx-kv sessiontask topic remove --cwd "<工作目录>"`（或 `--key <key>`）。
- **批量删除**：
  - 面板：勾选卡片左上角（或总览标题处「全选」）→「批量删除 (N)」；
  - CLI：`nx-kv sessiontask topic remove-many --keys "<key,key>"`，也可
    `--cwds "<dir,dir>"`，或 `--all` 清空。
- **安全保护**：等待中的主题默认不删（删了阻塞的 agent 只能等到超时）；界面会
  二次确认，命令需加 `--force` 才连等待中一起删，agent 随后超时收尾。
- **返回**：单个 `{status:"removed",topic}`；批量 `{count,removed,skipped}`，
  skipped 列出被跳过的「等待中 / 不存在」主题。

## 八、常见错误与避坑

| 错误做法 | 后果 | 正确做法 |
| --- | --- | --- |
| wait 后又安排别的工具/推理 | wait 阻塞，后续动作被卡住、顺序全乱 | wait 严格放在最后一步，之后只处理返回 |
| 工具超时没设/设太短（如 60s） | 宿主在回填前杀掉调用，任务中断 | 工具超时设 `120000` ms |
| wait 不带 / 空着 --summary | 无法定位等待点，命令报错退出 | 每次 wait 都写一句现状总结 |
| 同一现状却每次换措辞 | 被当成多个等待点，排队任务取不到 | 同现状用同一句总结，新现状才换新句 |
| 把不同阶段都写成同一句 | 不同现状无法分散，回填容易给错点 | 进入新现状就换新总结 |
| 把 timeout 当报错、反复重试 | 用户想停却被反复弹窗 | timeout 即收尾结束本轮 |
| 读 `task.id` 当任务内容 | id 只是编号，内容在 `task.text` | 一律读 `task.text` |
| 同时开多个 wait（同一等待点） | 只有一个收到回填，另一个等到超时 | 同一等待点同一时刻只调一个 wait |
| 没用 --json | 输出人读文本，宿主难以可靠解析 | agent 调用一律加 `--json` |

## 九、与常驻面板配合 / 排障

- 已 `nx-kv serve` 打开面板时，直接在「等待点总览」点选现状回填；正在阻塞的
  wait 通过轮询（约每 0.5 秒）取走，不依赖弹窗本身。
- 弹窗没自动打开时：终端输出里有本次地址（`http://127.0.0.1:<端口>/`），手动
  复制到浏览器打开；该窗口只在本次 wait 期间有效。
- wait 结束（拿到任务或超时）后弹窗服务器随即关闭，窗口里再提交会失败——下一
  条等 agent 下一次 wait 打开新窗口再给。
