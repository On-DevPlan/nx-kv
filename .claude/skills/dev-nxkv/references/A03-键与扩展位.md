# A03 · 键与扩展位：配置数据放哪、叫什么

> A 序列 · 底层数据结构之三。回答「这个值该落到哪个键位、谁是权威、哪些键已废弃」。
> 表结构见 [[A01-数据模型]]；关系见 [[A02-关系模型]]。

## 1. 四类落点，选错就是架构腐化

| 落点 | 存什么 | 形态 | 判据 |
|---|---|---|---|
| `config.json`（`~/.nx-kv/config.json`） | **凭据与会话身份** | 单文件 | 能不能泄漏？泄漏了要单独轮换吗？ |
| `settings` 表 | 全局偏好与全局开关 | k/v，value 是 **JSON 文本** | 全局生效吗？要不要进 `WHERE`？ |
| `<table>.ext` | **随行走的附属信息** | JSON 对象 | 跟着这条行走吗？会进 `WHERE` / 排序 / 唯一约束吗？ |
| `topics.ext` / `repos.ext` | 该行自己的旋钮与状态 | JSON 对象 | 同上，且**必须**是随行的 |

**硬规则**：凡是需要出现在 `WHERE` / 排序 / 唯一约束里的东西，**不许进 `ext` 或 `settings`**——它们无索引、查不动。凭据一律不进库（库会被 `VACUUM INTO` 备份、被 `db inspect` dump、被人拷走排障）。

## 2. `config.json` — 只放凭据

`CREDENTIAL_KEYS`：`baseUrl`、`token`、`email`、`userId`、`groupId`。

- **绝不**把偏好或提示词写进 `config.json`。
- 当前工作空间（`groupId`）的真相源在这里；面板**刻意不把它持久化到 localStorage**——存两份就会出现「面板显示 A 组、实际写进 B 组」。
- 路径可由 `--config` / `NX_KV_CONFIG` 覆盖（`src/core/config.js`）。

## 3. `settings` 表 — 全局偏好

| 键 | 含义 | 状态 |
|---|---|---|
| `app.autoSyncAttachments` | 附件自动同步开关 | 当前权威 |
| `app.attachmentsDir` | 附件目录根（默认 `~/.nx-kv/attachments`） | 当前权威 |
| `app.gitRepoRoot` / `app.gitDevRoot` | 参考仓库根 / 开发仓库根 | 当前权威 |
| `lt.timeoutSec` | 队列默认等待超时（秒） | 当前权威 |
| `lt.appendMode` | 全局追加模式：`xml`（默认，根标签 `<nx-kv>`）/ `plain`（正文按空行直拼） | 当前权威，整体生效 |
| `lt.blockTemplates` | **每个区块各自的模板列表**（见 §5） | 当前权威，保存即生效 |
| `lt.promptTemplates` / `lt.activePromptTemplate` | 云端主题提示词模板 | 当前权威 |
| `lt.deliveryTemplate` / `lt.attachTemplate` / `lt.taskSuffix` / `lt.ackPrompt` / `lt.xmlBlocks` | 旧版模板键 | **仅迁移来源**，不再作为读写模型 |

实现口径：

- 裸读写在 `src/core/db/settings.js`：`readSettingRaw` / `writeSettingRaw` / `deleteSettingRaw` / `listSettingsByPrefix`。
- value 一律 JSON 文本（`'180'` / `'["a","b"]'` / `'"…"'`）；JSON 损坏按「不存在」处理，脏数据不炸读取。
- `listSettingsByPrefix` 只给「整表导出/清理」用，**不当查询条件**。
- 域语义（clamp / 白名单 / 键名）留在各自模块，不下沉到 core。

## 4. `<table>.ext` — 随行附属

统一形态：JSON 对象，键名 `ext_` 前缀，`CHECK (json_valid(ext) AND json_type(ext) = 'object')`。

### 4.1 `repos.ext`（仓库 / 项目组 / 参考仓库）

| 键 | 含义 |
|---|---|
| `ext_legacy_id` | 旧 `r_xxx` / `b_xxx`（迁移取证 + 旧链接映射） |
| `ext_legacy_type` | `'ref'` = 这行是**参考仓库**（DB `repos.type` 没有 `ref` 值） |
| `ext_notes` | 随手记（与 `description` 是两个字段：一个是摘要，一个是随手记） |
| `ext_icon` | 图标 |
| `ext_remotes` | 原始远程地址列表（`remote` 是归一化后的主键来源，这个是原始多个） |
| `ext_key_custom` / `ext_key_updated_at` | 用户显式改过 key 的标记与时刻 |
| `ext_linked` | **仓库级参考绑定**（条目形如 `{kind, id, note}`）；v4 迁移会搬走其中已迁移部分，但仓库级绑定本身仍是合法落点 |
| `ext_linked_refs` | 旧键，等价于 `ext_linked` 里 `kind='ref'` 的条目（迁移来源） |
| `ext_getloop` | 项目级「持续 get」窗口配置（渲染进 `getloop` 区块） |
| `ext_doc` / `ext_doc_links` / `ext_repo_hints` / `ext_repo_docs` | 仓库自己的文档与提示 |

### 4.2 `topics.ext`（队列）

| 键 | 含义 |
|---|---|
| `ext_auto_wait` | 0/1：没有任务时 `get` 要不要自动转成等（默认 0 = 立刻返回空） |
| `ext_auto_wait_sec` | 自动等的超时秒数；到点直接返回空，不报错 |
| `ext_task_order` | 队列顺序（`seq` 数组）——看板/列表顺序**不在** `tasks.seq` 上 |
| `ext_workflow_state` / `ext_workflow_plugins` | 工作流引擎的快照与插件状态 |
| `ext_legacy_key` | 旧 `sha1(目录名)` key，仅取证，不解析别名 |
| `ext_global` | 全局池（`__GLOBAL__`）标记 |
| `ext_trash_index` | 回收站索引 |

队列级旋钮的优先级：**命令参数 > `topics.ext` > 全局 `settings.lt.timeoutSec`**。CLI 侧因此**只有 `get` 一个动作**：有任务就领，没任务且开了自动等就等，单次调用可用 `--wait / --no-wait / --timeout` 覆盖。

### 4.3 `tasks.ext`（任务）

| 键 | 含义 |
|---|---|
| `ext_deps_foreign` | **跨队列依赖**：元素形如 `"<topicKey>:<seq>"`（绝对地址，搬家不失效） |
| `ext_legacy_round_summary` / `ext_legacy_history` | 旧 JSON 迁来的历史（取证/兼容） |
| `ext_submit_summary` / `ext_last_summary` | 提交与完成回调摘要 |
| `ext_fork_of` / `ext_move_from` / `ext_migrated_to` / `ext_superseded_by` | 派生、搬迁、迁移的溯源指针 |

### 4.4 `templates` 表 vs 提示词模板 —— 两套，别混

| | 任务模板 | 提示词模板 |
|---|---|---|
| 落点 | `templates` 表 | `settings.lt.blockTemplates`（每个区块一份列表） |
| 内容 | 任务正文骨架（纯字符串槽位） | 交付提示词的区块模板（Handlebars） |
| 面板入口 | 设置页「任务模板」 | 设置页「提示词模板」 |
| 分类字段 | `category`（`newtask` 在用；`delivery`/`enhance`/`context` 是历史 seed 行，**不参与渲染**） | 区块 id（`context`/`attachment`/`timecheck`/`ext`/`ack`/`getloop`） |

`templates` 表的 `vars_schema`（**声明**有哪些变量、什么类型、怎么显示）与 `vars`（这些变量现在填的**值**）分工明确，别把默认值塞进声明里——同一件事不要有两个真相。

## 5. 区块模板列表的键结构

`settings.lt.blockTemplates` 的形状：

```text
blockTemplates[id] = {
  active: <当前生效项的 id>,
  list:   [ { id, name, template, builtin } , ... ]
}
```

- 六个区块：`context` / `attachment` / `timecheck` / `ext` / `ack` / `getloop`。
- 每个区块**始终至少有一个系统内置模板**：不可删除、不可编辑、可「恢复内置」；用户模板删到只剩内置时仍按内置渲染。
- 各块保存即生效；全局 `appendMode` 对所有区块整体生效。
- 存储、归一化、迁移与保存校验集中在 `src/modules/localtask/repo/settings.js` 与 `src/shared/prompt-blocks.js`（`BLOCK_DEFS`）。

详见 [[B04-提示词渲染链]]。

## 6. 设置键的迁移纪律

旧键（`lt.deliveryTemplate` / `lt.attachTemplate` / `lt.taskSuffix` / `lt.ackPrompt` / `lt.xmlBlocks` / 旧的整组模板键）**只作为迁移来源**，不再作为读写模型。

- 读旧库时由迁移把旧键映射到各区块的模板列表，并保证每块至少有一个内置模板。
- 旧 `rule` 区块（`lt.taskSuffix`、整组模板里的 `rule`、`lt.xmlBlocks.rule`、已落盘的 `blockTemplates.rule`）在首次读取时按空行并入 `ack` 当前生效模板（固定条目 `legacy-rule`），内容不丢；保存后只写六个区块键。
- **旧语法模板不迁移、直接跳过**——旧模板不保证可用。

## 7. 命名纪律

- `ext` 内键名一律 `ext_` 前缀；`settings` 内按前缀分域（`app.` / `lt.`）。
- `settings` 的键是**全局**的，不随行走；随行的东西放 `<table>.ext`。
- 凭据永远不进 `settings`。
- 队列级旋钮放 `topics.ext`，不要又塞回 `lt.*`——它们随主题走，`settings` 只放全局默认。
