# A01 · 领取任务（领取闭环：领 → 读 → 干 → 回填 → 按反馈派生下一轮）

## 这一篇解决什么

「我要干活」→ 领到活、读懂活、干完回填、用户提意见时正确派生下一轮。

**本质只有一条命令**：`nx-kv localtask get`。其余都是它的配套（读、回填、派生）。
不要先 `list` / `show` 翻队列再决定要不要领——那多两轮往返，还可能看到已被别人领走的任务。

## 三步

1. **领**：`nx-kv localtask get --cwd "<你的工作目录>"`（默认输出就是引擎封装好的 context 原文，逐字喂模型）。
2. **读**：先读交付里的 `instruction`（项目介绍 / 组上下文 / 附件本机绝对路径 / 收尾指令），再读任务正文；两者缺一都会返工。
3. **收尾**：`nx-kv localtask done --id <n> --summary "<改了什么 / 关键决策 / 遗留问题>"`。

## get 到底做了什么（机制，别猜）

| 环节 | 实际发生的事 |
| --- | --- |
| 认主题 | `--cwd` 决定 topic（一个 repo / repo+group 可定位唯一 topic）；不给 = 当前目录 |
| 挑任务 | 领的是**队首**（`get` 没有 `--id`，见下「领指定编号」） |
| 封上下文 | 项目/组介绍、附件本机绝对路径、时间目标 check 指令、收尾指令（ack 位）都拼进 `instruction` |
| 计时 | 带时间目标的任务**领取即起表**——那一刻就是既成事实 |
| 落状态 | 任务变 claimed，正文里插回执位 `<nx-kv.ack>` |

**三种结局，没有第四种**：

| 输出 | 含义 | 该做什么 |
| --- | --- | --- |
| 正文 + 状态行 | 领到了 | 干活 |
| `status=timeout` | 暂时没活（**业务结果**，exit 0） | 收尾，别重试刷 |
| `status=blocked` | 时间目标未到点 | 先 `timegoal check` |

参数只有四个：`--cwd`（默认当前目录）、`--timeout N`（阻塞上限，秒）、`--no-open`（不自动开面板）、`--param k=v`（进交付模板的扩展参数）。

## 读交付内容不要用 --json

交付的 `instruction` 是引擎**封装好的 context 原文**（提示词块 + `<nx-kv>` 类区块 + 回执位），不是给程序解析的数据。`--json` 会把整段变成一个 JSON 字符串、换行写成 `\n`；再拿 JSON 解析器去「读」它，看到的是一坨转义串——精心封装的上下文就等于丢了。

```bash
nx-kv localtask get            # ← 标准动作：stdout 就是逐字 context，原样喂给模型
nx-kv localtask get --xml      # 只取 instruction 逐字原样（脚本要单独拿这段时用）
nx-kv localtask get --json     # 仅当你要结构化字段（task.id / status 等）时用；
                                #   instruction 字段是转义后的 context，别再解析它
```

`--json` 与 `--xml` 互斥（同时给会报明确错误）。对交付类命令加 `--json` 时，CLI 会在 **stderr** 提醒你这句话（stdout 仍是纯 JSON）。

## 领指定编号（get 只能领队首）

```bash
nx-kv localtask show --id 42 --json                                    # 1) 确认内容与状态（只读，不领）
nx-kv localtask reorder --id 42 --before-id <队首 id> --json           # 2) 提到队首（也可用 --after-id）
nx-kv localtask get --cwd "<该任务所在目录>"                            # 3) 领走（必须带它所在目录）
```

- 目标任务可能属于**别的主题**（别的目录）：`get` 必须带那个目录的 `--cwd`，否则领到的是当前目录队列的队首。
- 不知道队首是谁：先 `nx-kv localtask list --json` 看该主题的待领取列表。
- 只要「看」不要「领」，做完第 1 步就停。

## 阻塞等人回填（本轮最后一步）

```bash
nx-kv localtask get --timeout 60
```

- `--timeout` 是**秒**（上限 600）：显式给定时，即使项目没开「持续 get」也真的阻塞这么久。
- 项目开了「持续 get」时，不给参数也会自动唤起阻塞窗口等人回填。
- 阻塞结束拿到 `timeout` = 没人回填，是业务结果不是失败：收尾即可。

## 时间目标（任务带 duration 时）

```bash
nx-kv timegoal check --cwd "<目录>" --task <id> --summary "<当前现状：做到哪了 / 剩什么>"
```

- 每轮开工前先 check 一次，`reached: true` 才允许 `done`。
- 未到点就 `done` 会被拒（`blocked / goal_not_reached`）——这是设计，不是 bug。
- 目录级预算是另一回事（整个目录跑多久）：`nx-kv timegoal set --cwd "<目录>" --duration 8h --prompt "<本轮整体目标>"`。

## 完成回填

```bash
nx-kv localtask done --id <n> --summary "<改了什么 / 关键决策 / 遗留问题>"
```

`--summary` 是**下一轮的唯一上文**：写给「没看过这段对话的人」看。写「已完成」等于没写。

## 用户提修改意见 → 派生下一轮（别自己 add）

```bash
nx-kv localtask reopen --id <n> --feedback "<用户原话>" --json
```

- `reopen` 的真实语义是**派生一条新编号的 pending 任务**（正文 = 旧正文 + 完成总结 callout + 反馈段）。
- 旧任务 done **保持 done**（claimed/pending → cancelled + supersededBy），链记在 `task_links`。
- 后续所有动作都用**新编号**；查链用 `nx-kv localtask chain --id <新 id> --json`。

## 草稿态（脑子里的想法，不进队列）

```bash
nx-kv localtask plan --id <n> --to plan      # 转草稿：get/wait/队列/闸门都看不到它
nx-kv localtask plan --id <n> --to pending    # 转回待领取，重新排队
```

只允许 `pending ↔ plan` 双向切换；`claimed/done/cancelled` 不许直接转。

## 偏差与陷阱

| 偏差 | 正确做法 |
| --- | --- |
| 先 `list` 把整队列打印给用户再 `get` | 直接 `get`；需要概览时才 `list` |
| 用 `show --id` 当领取 | `show` 只读，任务仍是 pending |
| `timeout` 当失败重试 | 它是业务结果（exit 0）——收尾，等下一轮 |
| 只读 `task.text` 不看 `instruction` | 组上下文 / 附件路径 / 收尾要求都是硬约束 |
| 用 `--json` 读交付再解析 | 那会让封装好的 context 变成转义串；用默认输出或 `--xml` |
| `done --summary "done"` | summary 是下一轮的唯一上文：改了什么、为什么这么定、还剩什么 |
| 用户提意见就 `reopen --text` 就地改 | `reopen` 是**派生新编号**；旧任务定格，后续用新编号 |
| 领指定编号时找 `get --id` | `get` 没有 `--id`：`show` → `reorder` 提到队首 → `get` |
| 给带时间目标的任务先 `done` 后补 | `done` 前先 `timegoal check`；未到点会被拒 |
| 想「先留着但别让人领」 | `localtask plan --to plan`，别用删除 |
