# A02 · SOP · 提示词模板体系与扩展（领取 → 讲透 → 规范扩展 → 检查点）

> 命中信号：交付给 agent 的提示词不对（少了一段 / 变量渲染成空 / 文案不像你要的）/
> 要给 agent **多一条上下文知识**（流程规则、必须遵守的约束）/ 要加一个新段落。
>
> 本篇是「提示词模板体系」的**唯一入口**：先把整套东西怎么转起来讲透，
> 再给**规范的扩展方法**与**每一步的检查点**。
> 区块 / 变量 / helper 的速查表在 `B03-提示词模板与上下文.md`。
>
> **#152 起体系是「插件制 + 正文进代码」**：一段 = 一个 `PromptPlugin` 子类，
> 模板正文就是这个类的 `templates` 常量，**没有** JSON 注册表、**没有** DB seed、
> **没有**顺序数组。设置页只读展示，用户在面板里**改不了正文**。

## ① 前置：先把现场看清楚

```bash
node bin/kv.mjs localtask get --cwd "<项目目录>"                 # 领一条（无活时阻塞到超时）
node bin/kv.mjs localtask get --cwd "<项目目录>" --timeout 60    # 阻塞上限（**秒**；缺省用项目配置）
node bin/kv.mjs localtask get --cwd "<项目目录>" --param k=v     # 外部参数进 ctx（{{k}} / {{params.k}}）
node bin/kv.mjs localtask preview --id <id>                     # 零副作用：看这条会交付什么（分段可追溯）
node bin/kv.mjs localtask show --id <id> --cwd "<项目目录>"      # 任务本体 + 附件清单与本地路径
node bin/kv.mjs prompt registry                                 # 注册表：时机链 / 每段正文 / 变量目录
```

`get` 的三个关键点：

| 点 | 说明 |
|---|---|
| **默认输出就是交付原文** | 读原文别用 `--json`（那是给程序用的形状，不是逐字原文） |
| **拿到就要按段落执行** | 交付里的 `ack` 段写明「完成后必须调用 `localtask done --id <id> --summary "…"`」 |
| **阻塞 ≠ sleep** | `--timeout N`（秒）是服务端挂住请求到点返回 timeout，不是让你自己等 |

## ② 领取并读懂交付

交付是**几段拼起来的 XML 块**（默认 `XML 标签` 模式；也可切成「纯文本直追加」）：

| 段（标签） | 内容 | 什么时候有 | 所属时机 |
|---|---|---|---|
| `<nx-kv.context>` | 仓库 / 组 / 参考仓库 / 其余组 | 登记了仓库就有（组材料只进**组任务**） | get |
| `<nx-kv.attachment>` | 附件清单 + 取用方式 + 文档原文 | 任务带附件时 | get |
| `<nx-kv.ext>` | 同主题还有多少待领取 | 队列非空时 | get |
| `<nx-kv.ack>` | 完成回填指令 | 总有 | get |
| `<nx-kv.getloop>` | 持续 get 指令 | 项目开了持续 get | get |
| `<nx-kv.timecheck>` | 时间目标检查指令 / 状态行 | 带时间目标时 | check |
| `<nx-kv.goalhint>` | 时间目标的可算上下文（过半 / 2/3 / 到点） | 带任务级时间目标时 | check |
| `<nx-kv.doneguard>` | 未到点不许 done 的拦截文案 | 目标时间未到（blocked）时 | done |

读的时候：先看 `ack`（怎么交差）→ 再看 `timecheck` / `goalhint` / `doneguard`（有没有时间门禁）→
再看 `context`（这个仓库/组是什么）→ 有附件先按附件段的「取用方式」读
（图片看图、md 读正文、**文件夹先列目录**再读里面的文件）→ 然后才动手。

## ③ 动作 · 体系总览：一条交付提示词是怎么转出来的（五个部件各管一段）

```
① 取数       任务 / 仓库 / 组 / 附件 / 队列 → 宿主取好，以 Supply 交给插件
② 建数据    每个插件的 buildData()：await supplied(...) → 只做变换，产出「纯数据」
③ 合并 ctx   compose() 按 order 逐段 get('data') → Object.assign 成一个大 ctx
④ 渲染       compose()：逐段 renderInstruction（模板 trim 为空 → 该段不出）
⑤ 包标签     XML 块（默认）/ 纯文本（appendMode 全局一个开关）
```

| 部件 | 位置 | 谁改 | 关键规则 |
|---|---|---|---|
| 段落（插件） | `src/modules/promptplug/plugins/*.ts` 的类 | 改代码 | `id` / `order` / `group` / `tag` / `label` / `dataSchema` / `writes` / `templates` / `buildData()` |
| **时机链** | 每个类的 `group`（`get` / `check` / `done`） | 改代码 | 一个 group = 一条链；链内按 `order` 升序；`order` 只需**链内唯一** |
| **模板正文** | 每个类的 `templates: readonly TemplateText[]` | 改代码 | 正文进代码（第一条 = 生效正文）；**无 JSON、无 DB、面板不可改** |
| 注册表 | `src/modules/promptplug/registry.ts` 的 `PLUGIN_CLASSES` | 改代码（加一行） | 唯一装配点：id / 链 / 顺序 / 模板 / 变量全部由类派生 |
| 装配 | `src/modules/promptplug/factory.ts` 的 `buildPlugins(group, deps, overrides)` | 改代码 | 按 group 造链；`deps` 是 `Supply`（值或惰性函数，可异步） |
| 变量目录 | `dataSchema` → `schema-bridge` → `registry.fields` | 改代码 | 数组元素也展开（`attach.list[].file.localPath`），多 kind 取并集 |
| 渲染 | `src/modules/promptplug/compose.ts` 的 `compose()` | 改代码 | **运行期不兜底**：`buildData()` / 渲染抛错 = 整次交付失败 |
| 引擎 | `src/core/instruction-template.ts` | 改代码 | `{{#if}}` / `{{#each}}` + 25 个 helper；`validateTemplate` 拒旧语法 |
| 设置面板 | `src/web/frontend/page/settings/prompt-templates-section.tsx` | 改代码 | 只读：时机链导航 + 内置正文 + 变量目录；**唯一可写的是 appendMode** |

> 交付时**三条链一起给**（get + check + done，合并后按各段 `order` 全局排序）：
> check（时间目标）与 done（完成门禁）没有独立的注入点——它们本来就是
> 「领取时告诉 agent 每轮怎么检查、什么时候才能收口」，等 agent 真去 done 再给已经晚了。
> 三者链内都是条件渲染，没数据就不出段。

## ④ 动作 · 规范扩展方法：三种动作（改文案 / 加变量 / 加段落）

先判定要做哪一种：

| 你要做的事 | 动作 | 落点 |
|---|---|---|
| 改某段的**说法**（文案风格、多加一句） | **扩展 1**：改类的 `templates` 正文 | 插件类里的 TS 常量 |
| 已有段落里多给 agent 一个信息 | **扩展 2**：给插件加变量 | `dataSchema` + `buildData()` + `templates` |
| 交付里多一段（新维度：规则、清单、提示） | **扩展 3**：加新插件 | 新类 + `PLUGIN_CLASSES` 一行 |

### 扩展 1 · 改一段的文案

| 步 | 落点 | 做什么 | 检查点 |
|---|---|---|---|
| 1 | 对应插件里的 `BUILTIN` 常量（如 `src/modules/promptplug/plugins/readonly-blocks.ts` 里 ack 那条） | 直接改 `text` | 条件渲染的段，**空数据必须整段不出现**（用 `{{#if}}` 包住，别印空标签） |
| 2 | 同一文件里 `templates = [BUILTIN]` | 不用动（第一条恒为生效正文） | 只有「多套内置模板」才加第二条 |
| 3 | `tests/unit/prompt-golden.test.mjs` | 跑一遍 | 渲染输出逐字比对；改文案要**同时**更新基线：`NX_KV_GOLDEN_WRITE=1` 重生成并 review diff |

> 文案改动是**全用户生效**的（正文在代码里），不存在「只改我这台机器」——
> 想按人定制就改 `appendMode` 或调整任务正文，不要打模板的主意。

### 扩展 2 · 给已有段落加一个变量

| 步 | 落点 | 做什么 | 检查点 |
|---|---|---|---|
| 1 | 插件类的 `dataSchema`（`z.strictObject`） | 声明字段（可选 `.optional()`，并写 `.describe('给用户看的一句话')`） | 严格对象：多写的键会被 `get('data')` 的 safeParse 拒 |
| 2 | 同一个类的 `buildData()` | 从 `Supply` 取数并投影成**纯数据**字段 | 字段名与业务词一致（`repo.introRefId`，不是 `repo.intro_id`） |
| 3 | 需要写回 ctx 才加 `writes` | 默认 `writes = []`（只读段不回写） | 只读段不参与 ctx 合并，但仍可读 seed |
| 4 | 该类的 `templates` 正文 | 加占位 `{{新字段}}`（必要时加 `{{#if}}` 闸门） | 空数据时整段不出现 |
| 5 | 内置 skill（`assets/nx-kv/references/`） | 写给 agent 的用法（什么时候用这个变量） | agent 看得懂这条信息是干嘛的 |

> 前端**不需要登记**：设置页「可使用变量」由 `GET /api/prompt/registry` 的 `fields`
> （`schema-bridge` 从 `dataSchema` 派生）直接渲染，没有第二份手写表。

### 扩展 3 · 加一个新段落（新插件）

| 步 | 落点 | 做什么 | 检查点 |
|---|---|---|---|
| 1 | `src/modules/promptplug/plugins/` 新建类，继承 `PromptPlugin` | 写 `id` / `order`（链内唯一）/ `group`（`get`/`check`/`done`）/ `tag`（`nx-kv.<id>`）/ `label` / `dataSchema` / `templates` / `buildData()` | 漏写抽象成员 → tsc 直接报错 |
| 2 | `src/modules/promptplug/registry.ts` 的 `PLUGIN_CLASSES` | 加一行 import + 一行登记 | 加完跑 `assertRegistry()`（单测会跑）：id 唯一 / 链内 order 不撞 / 模板非空 / 写回段不撞车 |
| 3 | `src/modules/promptplug/factory.ts` 的 `buildPlugins` | 在该 group 的 `switch` 分支里 `new 你的类(...)` | 漏了这步 = 类永远不被构造（注册表看得见、交付里没有） |
| 4 | 若需要宿主取数 | 在 `DeliveryPluginDeps` 加一个 `Supply`，由 tasktool 侧传 | 懒求值：不消费就不算（大对象别提前拷） |
| 5 | 内置 skill | 告诉 agent 这段是干什么的 | — |

> 设置面板**不需要额外登记**：左轨按 `groups` 铺开，正文与变量都从注册表读。

## ⑤ 检查点清单（扩展完必过，逐条有判据）

| # | 检查点 | 判据 | 怎么验 |
|---|---|---|---|
| 1 | **模板语法** | 没有旧语法（`{{#section}}` / `{{^x}}`）；`{{#if}}`/`{{#each}}` 闭合 | `tests/unit/prompt-blocks.test.mjs`（含废弃语法拒绝） |
| 2 | **变量解析** | 新占位符渲染出**真实内容**，不是空串 | `localtask preview --id <id>` 目视（**变量名写错不会报错，只会静默变空**） |
| 3 | **变量目录可见** | 设置页「可使用变量」查得到新字段；数组元素显示为 `x[]` | `node bin/kv.mjs prompt registry`；`tests/unit/attach-schema.test.mjs` 同类断言 |
| 4 | **空数据闸门** | 数据为空时该段**整段不出现** | `preview` 一条没有该数据的任务 |
| 5 | **老交付没坏** | 原有各段的输出与改动前**逐字一致** | `tests/unit/prompt-golden.test.mjs` |
| 6 | **schema 与真实形状一致** | `buildData()` 的产物过 safeParse（不是「差不多」） | 该插件的单测拿真实变换产物去 `get('data')` |
| 7 | **门禁** | lint / typecheck / 单测 / smoke 全绿 | `pnpm lint`、`pnpm typecheck`、`pnpm test:unit`、`pnpm test:smoke` |
| 8 | **说明书** | 内置 skill 写清了新字段/新段落的用法 | 人工过一遍 |

> 第 2、4 条是**目前唯一能发现变量写错**的手段（未知变量渲染成空串，不报错）——
> 所以 `preview` 不是可选项，是扩展的必过关口。

## ⑥ 现状体检：这套东西现在的约束（#152 后）

| 事实 | 位置 | 含义 |
|---|---|---|
| 运行期**不兜底** | `compose()` + `assertPluginList` | 空模板 / 坏模板 / schema 不符都在启动期或该次交付直接抛错。**故意**如此：静默回落会让「少半段」无人知晓 |
| 模板正文只有一份 | 各插件类的 `templates` | 没有 JSON 注册表、没有 DB 行、没有「内置 + 用户条目」两套；改文案 = 改代码 |
| 顺序不是数据 | 各插件类的 `order` | 链内唯一即可，跨组无要求；没有「拖动排序」也没有落库 |
| 时机即链 | 各插件类的 `group` | 交付 = get + check + done 三条链合并（按 order 全局排序） |
| 变量知识只有一份 | `dataSchema` → `registry.fields` | 前端目录、模板白名单、CLI/HTTP 校验同源 |
| 宿主取数是 Supply | `factory.ts` 的 `DeliveryPluginDeps` | 值或惰性函数；异步留给 HTTP 类取数（云端提示词） |
| 无附件时 `attach` 为 null | attachment 插件 `dataSchema` | 整段不输出（不是空清单） |

## ⑦ 自检

```bash
node bin/kv.mjs localtask preview --id <id>      # 零副作用看渲染结果：分段 + 告警
node bin/kv.mjs localtask get --cwd "<项目目录>"  # 真领一次，看最终交付原文
node bin/kv.mjs prompt registry                  # 时机链 + 每段正文 + 变量目录
pnpm lint && pnpm typecheck && pnpm test:unit
```

| 检查 | 通过判据 |
|---|---|
| 领取流程 | 交付里段齐全、顺序符合各段 `order`；`ack` 段要求回填 |
| 扩展生效 | 新段/新变量在 `preview` 里出现且**有内容** |
| 老交付一致 | `prompt-golden` 全绿（基线变更必须在 diff 里 review 过） |
| 坏模板 | 启动期/交付时直接抛错（不是静默回落） |
| 门禁 | lint / typecheck / 单测 / smoke 全绿 |

## ⑧ 失败分支

| 症状 | 原因 | 处置 |
|---|---|---|
| 新变量渲染成空 | 变量名写错 / `buildData()` 没投影 / 不在该段的 `writes` 下 | 对照 `prompt registry` 的 fields；`preview` 看渲染结果 |
| 交付里出现空标签（`组定位：`） | ctx 字段存在但内容为空 | 给出默认文案，或用 `{{#if}}` 整段闸掉 |
| 设置面板没有「编辑正文」 | **设计如此**：#152 起正文在代码里 | 改插件类的 `templates`，重启面板后只读展示会跟着变 |
| 改了类里的模板，交付没变 | 该类还没登记进 `PLUGIN_CLASSES` / `buildPlugins` 没构造它 | 补登记 + 补 factory 分支，跑 `assertRegistry()` |
| **领取整单失败** | 设计如此：`buildData()` 抛错 / schema 不符 / 渲染抛错不回落 | 看报错里的段 id 与 zod issues（`<id>: buildData() 返回与 schema 不符——…`） |
| schema 突然报「expected string, received undefined」 | 宿主给的数据形状变了（新增 kind / 字段改名），schema 没跟上 | 用真实变换产物补字段（附件 6 种 kind 各有子对象就是范例） |
| 新段落在面板上看不到 | 没登记进 `PLUGIN_CLASSES` | 补登记；`groups` 由注册表派生 |
| 顺序与预期不同 | 链内 `order` 撞车 / 跨链按 order 全局排序 | `assertRegistry()` 会报「order 冲突」 |

## ⑨ 反模式

- 在 ctx 里塞**成文措辞**（ctx 只放数据；措辞在模板里）。
- 在代码里再加一份模板常量（第二份真相；正文只在插件类的 `templates`）。
- 用 `z.looseObject({})` 把复杂结构抹平（校验失效、变量目录全空——附件的 6 种 kind 就被这么坑过）。
- 新增字段不 `preview` 就提交（变量写错不报错，只会静默变空）。
- 用 `try/catch` 给渲染加回落（明确删除：静默降级比失败更贵）。
- 把「每轮都要说的规则」塞进任务正文（正文会被重排，规则会沉底）。
- 把「一次性要求」塞进全局模板（所有任务都被污染）。
- 为了让某段出现，去改**别的**段落模板（段各有职责，串味了没人查得出来）。
- 给 `order` 手写 10 的倍数当「位置」（它只是链内排序键，不是数组下标）。
