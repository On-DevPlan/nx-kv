### 1.1 知识型文档的腐烂实锤（全部为当前 HEAD 实测）

| skill 里的断言 | 代码事实 | 结论 |
|---|---|---|
| B02 标题「154 条入口」、SKILL.md「157 条 = 154 action + 3 平台命令」 | `help --json` = **129 条**（126 action + 3 平台命令） | 数字过期 |
| A01「`CURRENT_SCHEMA_VERSION = 4`」 | `src/core/db/version.ts` = **8**，migrations 已到 `v8.sql` | 数字过期 |
| E01 §7「同步 `assets/`（`nx-kv/`、`kv-get/`、`kv-submit/`、`kv-repo/`）」 | `assets/` 下**只有 `nx-kv/`**（四合一早已合并） | 结构过期 |
| B02 §3 手抄 205 行 action 表 | `pnpm gen` 已生成 `_manifest.generated.ts` + 前端 typed client | 重复真相源 |
| B02 §3.3 `auth`（4 条）、§3.9 `todo`（25 条） | `src/modules/` 只有 10 个模块，**`auth` 与 `todo` 已不存在**（v7 本机化时删除） | **29 条幽灵条目** |
| 95 处反引号路径中 2 处不存在 | `src/core/attachstore.ts`、`src/core/fileapi.ts` | 断链 |

其中最严重的不是数字过期，而是 **29 条幽灵条目**：agent 读到 `auth.…` / `todo.…` 会照着执行，命令不存在、报错、再换一条，形成无效循环。这正是「知识库式 skill」最坏的失效模式——它不是不帮你，而是主动误导。

这五类错误（计数、常量、目录结构、全表、路径）**全部可被一个脚本抓住**——它们不是写作质量问题，是「手抄第二真相源」的必然结果。

## 3. 重构方向（三个候选）

### 方向 A（推荐）：场景化 SOP + 生成式地图 + 新鲜度门禁

**核心判断：把「会腐烂的知识」变成「编译产物 + 断言」，把「不会腐烂的判断」变成「症状→动作」。**

```
.claude/skills/dev-nxkv/
  SKILL.md                  # ≤60 行，只做路由：触发条件 + 3 条硬约束 + 场景→T 表
  references/
    T01-加一条命令.md        # action（CLI + HTTP）分步动作
    T02-加一张表或列.md      # migration + 决策文件 + 回滚
    T03-加面板页面.md        # page/registry/panels/routes 四登记点
    T04-改提示词模板.md      # 保存期 + 运行期两层验证
    T05-改依赖与编排.md
    T06-改内置技能与文档.md  # assets/ + README + CHANGELOG 同步
    T07-交付验证.md          # 合并现 E01+E02，固定命令清单
    T08-排障.md              # 现 E03 改写：症状 → 判定命令 → 处置动作
    M01-数据地图.md          # 生成物：表/列/关系/migration 边
    M02-入口地图.md          # 生成物：126 action 全表（替代 B02 手抄 205 行）
    M03-前端地图.md          # 生成物：页面 ↔ 组件 ↔ /api ↔ hash
    M04-约束地图.md          # 半生成：分层禁列 + 4 道门禁的实际规则
```

**每条 T 的固定骨架**（这是「动作 SOP」的可执行定义）：

```markdown
## 触发        什么请求落到这条
## 前置        最小读取集（几个 M0x + 具体文件路径），不是「读完全部 A/B/C/D」
## 动作        1..n 步，每步一条可复制命令 / 一处明确编辑点
## 证据        命令 + 期望输出（不是「应该通过」）
## 失败分支    症状 → 原因 → 处置（链 T08）
## 门禁        本改动必须跑哪几段 pnpm
```

**两个新脚本（把知识变成产物）**：

| 脚本 | 产出 | 吃掉现有内容 |
|---|---|---|
| `scripts/gen-skill-map.mjs` | M01/M02/M03 | B02 全表、D02 页面↔API、A01 表清单 |
| `scripts/check-skill-freshness.mjs` | 门禁 | 抓本次发现的 5 类腐烂：命令数、schema 版本、assets 目录、路径存在性、生成物是否过期 |

`check-skill-freshness` 挂进 `pnpm lint`，规则示例：

- `CURRENT_SCHEMA_VERSION` 必须与 `src/core/db/version.ts` 一致
- skill 里出现的 `assets/<name>/` 必须真实存在
- skill 里出现的 `src/**`、`tests/**` 路径必须存在（白名单容纳「新建的文件」示例）
- M01/M02/M03 的哈希与代码不一致 → 提示 `pnpm gen:skill`

**取舍**：成本是约 250 行脚本 + 一次全量改写；收益是消掉 1100+ 行手抄表格、把「过期」从人工发现变成 CI 失败。
风险是「为什么这么设计」会流失 —— 处置方式：理由只留 `docs/decisions/`，SOP 里只写一行「理由见 @decision <文件>」，不复制。

### 方向 B：极简，只留 8 条 SOP

砍掉全部 A/B/C/D 知识，只保留 T01–T08，知识一律现读代码或 `routes/help --json`。

- 优点：加载成本最低（约 400 行），零腐烂面。
- 风险：agent 每次都要现场摸索「哪个文件归哪层」，token 反而更高；同时丢掉 E03 坑库的防御价值（那些是付出过代价的）。
- 适用：如果确认「agent 只做小幅改动」，B 足够。

### 方向 C：物理拆成两个 skill

`dev-nxkv`（SOP，约 500 行）+ `nxkv-map`（纯地图，全部生成）。
结构上是 A 的子集，额外收益是地图可按需加载、可被别处复用；代价是两个 skill 的安装/同步成本。

## 4. 推荐路线（A + C 的加载优势）

**P0 · 止血**（1 次提交，不动结构）：修掉已确认的 5 处过期（157/154 → 129/126、v4 → v8、assets 四目录 → 一目录、2 处断链路径），并在 B02 标题注明「本表为快照，权威源 `nx-kv routes --json`」。

**P1 · 地图变产物**：写 `gen-skill-map.mjs`，产出 M01/M02/M03；删掉 B02 的手抄表体，只留生成说明 + 指向生成物。

**P2 · 知识二分**：A/B/C/D 逐文件判断——可生成 → 并入 M 序列；不可生成（分层判断、坑库）→ 拆进对应 T 的「前置/失败分支」。

**P3 · SOP 成篇**：E01+E02 合并为 T07；E03 改写为 T08（每条坑补「判定命令」与「处置动作」）；新增 T01–T06。

**P4 · 上门禁**：`check-skill-freshness.mjs` 进 `pnpm lint`；SKILL.md 重写成纯路由。

## 5. 验收标准（重构完成后逐条可验证）

- [ ] `SKILL.md` ≤ 60 行，只含触发条件、硬约束、场景→T 路由表
- [ ] `references/` 内「可执行命令行 / 总行数」≥ 25%（现状 1.2%）
- [ ] 零手抄计数：skill 里不出现「N 条 action」「schema = N」这类常量（全部来自生成物或门禁断言）
- [ ] 每条 T 都有「证据」小节，内容是命令 + 期望输出
- [ ] 每条 T08 坑都有「判定命令」与「处置动作」，不只是「原因分析」
- [ ] `pnpm check:skill` 能复现并抓住本次发现的 5 类过期
- [ ] `pnpm test` 全绿（129 → 130+ 单测，含 freshness 的自测）
