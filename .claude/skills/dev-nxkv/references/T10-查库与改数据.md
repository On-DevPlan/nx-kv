# T10 · 查库 / 改本机数据

> 只读随便查；**写入先备份，且优先走现成命令**——手写 UPDATE 是最后手段。

## ① 前置（30 秒把家底摸清）

```powershell
node bin/kv.mjs db status                 # 库路径 / schema 版本 / 行数概览
node bin/kv.mjs db verify                 # 结构 + 一致性校验
node scripts/db-inspect.mjs --tables      # 每张表与行数
node scripts/db-inspect.mjs --topics      # 队列概览
```

库位置：`NX_KV_DB` 优先，否则 `<APP_DIR>/nxkv.db`（通常 `~/.nx-kv/nxkv.db`）。
附件字节不在库里：`~/.nx-kv/attachments/local/`（`NX_KV_ATTACHMENTS` 可覆盖）。

## ② 只读查询（首选工具）

```powershell
node scripts/db-inspect.mjs --table tasks --limit 5
node scripts/db-inspect.mjs --sql "SELECT status, count(*) c FROM tasks GROUP BY status"
node scripts/db-inspect.mjs --json | ConvertFrom-Json     # 脚本里用
```

`db-inspect` 与 `db status` 的分工：前者「翻数据」，后者「一眼看状态」。**两者都不触发导入、不改库**——排障工具顺手改库是最糟的设计。

要更自由的查询：

```powershell
node bin/kv.mjs db status --json     # 先确认拿到的是哪个库
```

## ③ 动作：要改数据时

**Step 1 先判断能不能用现成命令**

| 想做的事 | 用命令 |
|---|---|
| 改任务状态 / 领取 / 完成 / 重开 | `localtask commit` 系（`get` / `done` / `reopen` / `cancel`），**不要手改 `status`** |
| 改设置 | `localtask config` / `setting set` |
| 换仓库路径 / 归组 | `repo` / `board` 命令 |
| 重建派生字段 | 找对应 service 的重算入口（如 `docs` 的 rescan），别自己拼 UPDATE |
| 删数据 | 软删命令（`remove` / `prune`），`task restore` 可恢复 |

**Step 2 必须备份**

```powershell
node bin/kv.mjs db backup         # 内部 VACUUM INTO，WAL 下唯一安全做法
```

直接复制 `.db` 会拿到不一致快照——`.db-wal` 里还有未落盘的内容。

**Step 3 真要手写 SQL**

```powershell
# 用临时副本练手，别在真库上试
Copy-Item ~/.nx-kv/nxkv.db temp/try.db
$env:NX_KV_DB="temp/try.db"
node scripts/db-inspect.mjs --sql "UPDATE tasks SET status='pending' WHERE seq=12"
node bin/kv.mjs db verify
Remove-Item Env:\NX_KV_DB
```

规矩：
- 语句带**唯一条件**（`id` 或 `seq + topic_key`），不写 `WHERE 1=1`。
- 一次改一行；批量要跨行先想清楚事务边界。
- 改完跑 `db verify`，并重新看一遍 `db-inspect --topics`。
- 派生字段（如 `blockBy` 的另一侧、`ready`）不要手改，让 service 重算。

## ④ 自检

| 检查 | 命令 | 判据 |
|---|---|---|
| 备份可读 | `ls ~/.nx-kv/*.db*` | 备份文件大小合理、时间是最新 |
| 结构完好 | `db verify` | 无错 |
| 数据符合预期 | `db-inspect --sql "…"` | 目标行数与值正确 |
| 没污染别处 | `db-inspect --tables` | 其他表行数未异常变化 |
| 队列仍可用 | `localtask list --json` | 主题与计数正常 |

## ⑤ 失败分支

| 症状 | 原因 | 处置 |
|---|---|---|
| `db status` 显示版本比代码低 | 没迁移 | `db migrate --dry-run` → `db backup` → `db migrate` |
| 备份后恢复不了 | 复制的是 `.db` 而非 `VACUUM INTO` 产物 | 只用 `db backup` 的产物 |
| 手改后任务「消失」 | 改坏了 `deleted_at` / `status` | `task restore` 或从备份恢复 |
| 附件打不开 | `local_path` 指向的文件已被移走 | `file orphans` 查无主资源，重新上传 |
| 改了但界面没变 | 面板读的是缓存 / 别的库 | `db status --json` 确认库路径与 serve 一致 |
| 测试写脏了真实库 | 没设临时库 | 立刻 `db backup`；之后测试一律 `tests/support/test-store.mjs` |

## ⑥ 红线

- **禁止** `DELETE FROM tasks` / `DROP TABLE` 之类的整表操作，除非你刚做完备份且明确知道后果。
- **禁止**删 `.db-wal` / `.db-shm` 试图「修复」——先关进程，再 `db verify`。
- **禁止**把凭据写进库（凭据只在 `config.json`）。
- 任何对真实库的写操作，都要在汇报里写明：改了哪几行、依据什么、怎么回滚。
