# A06 · 参考仓库驱动的开发：结合组、组内项目与参考仓库写自己的源码

## 这一篇解决什么

用户说「**参考** 参考仓库」「**照着** XX 仓库做」「看看 XX 是怎么实现的，用到我们这」——
你要做的不只是「读一个仓库」，而是**把参考仓库的做法消化进自己源码的开发里**。
本篇给出固定的读取顺序（四层降级：组主篇 → 具体参考仓库 → 组内案例检索 → 落自己源码）与读后的收尾动作（补全组内定位）。

## 触发时机（平时挂着，见到这些话就进本 SOP）

- 「参考 参考仓库」「参考 XX」「照着 XX 做」「借鉴 XX」
- 「看看 XX（参考仓库名）是怎么实现 Y 的」
- 「我们仓库里有没有能参考的」/「组里有什么能用的」
- **以及所有「开始实现 Y」类任务的前置动作**：知道定位之后、动手之前，
  第一思考永远是「组内有没有现成的案例实现」——参考仓库与组内其他开发仓库都是案例库。

## 硬规矩（三条）

1. **先读组的主篇，再读具体参考仓库**——组主篇是 get 交付时默认带进 context 的「重要空间」，
   里面是整个组的地图（各项目的定位、每个参考仓库参考什么）。跳过它直接翻参考仓库源码，
   大概率重复劳动。
2. **交付 context 里已经带了大部分答案，不要重复查**：`localtask get` 的交付正文里
   `〔项目上下文〕` 段已包含组主篇全文 / 各成员定位（`group.note`）/ 参考仓库清单
   （`refRepos`：key / name / **本地绝对路径**）。先读 context，缺什么再补什么命令。
3. **读完必须回写**：消化完参考仓库后，把新理解**补全进组的定位材料**（组主篇或组内描述）——
   「读完就走」会让下一个 agent 重读一遍同样的源码。

## 一、四层降级的读取顺序

### 第 1 层 · 组主篇（先看地图，别先翻仓库）

组主篇（组介绍 ref）在 get 交付的 context 里**默认全文出现**——它就是本次任务最重要的空间：

- 有组主篇全文 → 直接在里面找：这个组是干什么的、组内各项目的定位（`group.note`）、
  每个参考仓库「参考什么」的说明。
- context 里只有引用没有全文（主篇缺失 / 未绑定）→ 按需补查：

```bash
nx-kv docs list --json                          # 自有文档索引（找组主篇）
nx-kv docs get --ref ref:<refId>                # 读组主篇全文（逐字正文）
nx-kv docs bindings --host <组key> --json       # 看这个组绑了哪些篇
```

### 第 2 层 · 具体参考仓库（地图上没有 / 不够细才来这层）

组主篇对某个参考仓库只有一句话甚至没提 → 自己读它。参考仓库的本地绝对路径已在
context 的 `refRepos` 清单里（key / name / path），**直接读本地文件**，不需要再查地址：

```bash
# 先看有没有现成主篇（入库时应该写过「概念 + 关键代码」分析）
nx-kv docs bindings --host <参考仓库key> --json      # 该参考仓库的文档列表
nx-kv docs get --ref ref:<refId>                     # 有主篇就读主篇（省一遍源码）

# 主篇没有 / 不够细 → 实读源码（只读，不改动参考仓库）
# path 就是本地绝对路径：README → 入口文件 → 与任务相关的模块
```

**怎么读**：带着当前任务的问题去读（「这个任务要做的 Y，XX 仓库是怎么做的」），
产出三样东西——**概念模型**（它怎么划分职责）、**关键代码**（文件 + 为什么这么写）、
**可搬运点**（哪些做法能对到我们的源码）。

### 第 3 层 · 组内案例检索（动手前的第一思考）

知道定位之后，**在写第一行自己的实现代码之前**，先搜一遍组内有没有现成的案例实现——
参考仓库是「别人怎么做」，**组内其他开发仓库是「我们自己已经怎么做过的」**，后者优先级更高
（同约定、同依赖、可直接对齐）。两条搜索线都走一遍：

```bash
# 参考仓库线：refRepos 清单给的本地绝对路径里搜关键词（实现概念的中英文名都试）
rg -n "<关键词>" <参考仓库path>/src

# 组内开发仓库线：context 的 group.peers 清单给的本地路径里搜同关键词
rg -n "<关键词>" <组内其他仓库path>/src
```

搜什么：任务要做的能力的**概念名**（如需要轮询就搜 `interval` / `poll` / `retry`）、
**它属于的模块名**、**相邻功能的命名**（找同类已实现功能看它挂在哪）。

- 找到案例 → **优先对齐**：抄结构（它怎么拆职责 / 怎么处理边界 / 怎么接 CLI 与面板），
  实现按我们仓库的现状改写；`done --summary` 里注明「复用了 X 仓库的 Y 案例」。
- 没找到 → 回第 2 层的参考仓库找可搬运点；都没有才从零设计，并在 done 里说明
  「组内无先例，按 XX 参考仓库的模式新建」。

### 第 4 层 · 落进自己的源码

把「可搬运点」翻译成自己仓库的改动。注意：

- **按自己项目的结构落地**，不是照抄目录布局——概念对齐，实现贴着自己已有的约定走。
- 改动完成后，`localtask done --summary` 里**注明参考了哪个仓库的哪部分**（哪一段设计
  被采纳、为什么），方便后续轮次与用户验收时追溯。

## 二、读后的收尾：补全组的定位（必做）

读完参考仓库（或组内其他项目）后，把新理解写回去。按「缺什么补什么」：

### 1）某个成员仓库在组里的定位没写 / 过时

```bash
nx-kv board note --id <仓库key> --board <组id> --note "<它在这个组里负责什么、与谁配合>" --json
```

### 2）组主篇里缺这个参考仓库的介绍 / 「参考什么」过时

组主篇是**一篇**（换位制，主篇唯一）。把新理解**追加进组主篇正文**的对应小节
（不要另起一篇），然后原位更新：

```bash
nx-kv docs set --ref ref:<组主篇refId> --body-file <更新后的组主篇.md> --json
```

### 3）「各项目在这个组当中的定位」整体缺失

在组主篇里补一节「**组内分工**」：每个成员仓库一行（key + 一句话定位 + 与其它成员的关系），
每个参考仓库一行（key + 参考它的什么）。这就是组主篇作为「重要空间」的核心价值——
下一个 agent get 到任务时，不用再翻任何源码就知道整个组的布局。

## 三、常见变体

| 情形 | 动作 |
| --- | --- |
| 用户只说「参考 XX」，但 XX 没在本机 | 先走 [[A04-仓库与项目组]] 的克隆 SOP（六步），再回本篇第 1-3 层 |
| 组主篇说「参考 XX 的登录实现」，但源码里找不到 | 用 `docs bindings --host <XX 的 key>` 看它有没有更细的分析篇；没有就实读源码，并**把找到的入口写回组主篇**（下次不再找） |
| 参考仓库的主篇过时（与源码对不上） | 以源码为准；顺手更新主篇（`docs set --ref`），这是入库纪律（[[A04-仓库与项目组]] §八） |
| 参考仓库很关键，值得常驻 context | 组主篇里给它写清「什么时候读它的哪部分」——比把全文塞进 context 更省 |

## 四、偏差与陷阱

- **跳过组主篇直接翻参考仓库源码**：最常见的偏差——context 里已有组主篇全文还去跑
  `docs list`。先在 context 里找，找不到才补命令；补之前想想是不是真的缺。
- **照抄目录布局**：参考仓库的结构是它自己的约定；落地时对齐的是**概念**（职责划分、
  数据流向），文件组织贴着自己仓库已有的分层走。
- **读完不回写**：三样产出（概念模型 / 关键代码 / 可搬运点）只留在本轮对话里，下个
  agent 到了同一场景还要重读一遍源码——务必把结论落进组主篇或 `board note`。
- **在参考仓库里动手**：branch / commit / stash 都不行。要实验就在自己仓库开临时分支，
  或把需要的片段抄进自己的工作树（注明来源）。
- **把「参考」做成「照搬」**：参考仓库的实现可能依赖它自己的运行环境（依赖版本 /
  平台 API）；搬运前先确认我们这边有对应条件，没有就先写进任务正文作为前置问题。

## 五、边界

- 参考仓库**只读**：任何修改（branch / commit / push）都不许发生在参考仓库里。
- 不要把参考仓库的文档搬进自己的仓库——引用关系（组主篇 / 绑定）就够了，复制会产生两份真相。
- 组内「谁参考谁」的权威数据在**绑定关系**（`repo bind`）与**组主篇正文**；本篇不新增第三处。
