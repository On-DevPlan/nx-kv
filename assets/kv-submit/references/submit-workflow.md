# submit-workflow — 需求提炼与委托提交的完整 SOP

> 归属 [[kv-submit]]。当你要把当前对话里的需求委托给别的 agent 时，按本 SOP 走。

## 一、什么时候提交 / 委托

| 信号 | 动作 |
| --- | --- |
| 用户明说「交给 xxx 那边的 agent」「让另一个项目去做」 | 提交到那个项目的目录 |
| 用户给的需求属于另一个项目/目录的职责范围，且那边有 agent 在工作 | 先向用户确认目标目录，再提交 |
| 用户想给一个**正在等待**的 agent 追加/更正任务 | add 到它的目录（正在 wait 的约 0.5 秒内取走） |
| 目标目录暂时没人，但用户想先把任务存上 | 照常提交——任务排队，等那边的 agent 下次领取 |

不要在目标不明时猜目录：`--cwd` 错了任务就沉进没人看的队列。**不确定就问。**

## 二、三步提炼法

### 1. 总结上下文（挑相关的）

从当前对话里摘出与需求直接相关的：

- 已做的决策（「用方案 B」「不改现有 API」）；
- 涉及的文件/目录/服务的**完整路径**；
- 相关约定（分支名、命名规则、兼容性要求）。

流水账、被否决的方案、与本需求无关的支线——都不要带。

### 2. 提炼用户需求（收敛成一句目标）

把用户分散的、口语化的表述收敛成：

- **一句目标**：「做什么、为什么」；
- **验收标准**：做到什么程度算完成（可观察、可检查）；
- **显式边界**：不要做什么。

有歧义（比如「优化一下」没说优化什么指标）→ 先向用户确认，**不要把猜测提交
出去**。提交前把提炼结果给用户过目。

### 3. 打包成自包含任务文本

模板（单行，①②③ 编号；总长 ≤20000 字）：

```
①目标：<做什么，做到什么程度算完成> ②背景：<相关路径（写全）、已定决策、约束>
③注意：<不要做什么、已知坑（没有就省略）>
```

示例：

```
①目标：把 src/api/auth.js 的登录超时从 30s 改为 120s，并补对应单测，跑通全量测试
②背景：仓库在 D:\code\a_js\proj\demo；超时逻辑集中在 auth.js 的 TIMEOUT 常量；
测试用 pnpm test；不要动 token 刷新逻辑（上周刚重构过）
③注意：Windows 换行，改完别动文件结尾的 BOM
```

**为什么必须自包含**：接收方看不到你的对话。「如上所述」「刚才说的那个文件」
到它那里都是空引用。

## 三、提交命令与返回

```bash
nx-kv localtask add "<任务文本>" --cwd "<目标工作目录>" --json
```

- `--cwd`：接收方 agent 的**工作目录**（主题按目录名识别，Windows 折叠大小写；
  同名目录共用队列）。
- `--summary "<现状>"`：可选，顺带刷新该主题在面板/弹窗顶部展示的现状。
- 文本含空格必须加引号；跨执行边界传长文本时优先保持**单行**（多行参数可能
  被平台切掉后半截），用 ①②③ 编号替代换行。

成功返回 `{status:"ok", key, cwd, name, summary, task:{id,text,status:"pending",createdAt}, delivered, queued}`：

| 字段 | 含义 |
| --- | --- |
| `task.id` | 任务编号（该队列内自增），向用户报告用它 |
| `queued:true` | 已入队（跨进程提交的常态）；那边正在 wait 的 agent 约 0.5 秒内取走 |
| `delivered:true` | 提交进程内正好有 wait 在等、当场送达（罕见） |

文本非法（空、超 20000 字）或目录非法 → 报错 exit 1，按错误处理并修正后重试。

## 四、提交后：拆分、排序、跟踪

- **大需求拆多条**：每条一个可独立完成的单元，按执行顺序逐条提交（同一队列
  按提交先后领取）；发现顺序不对用
  `nx-kv localtask reorder --id <n> --before-id <m> --cwd "<目录>"` 校正。
- **查状态**：`nx-kv localtask list`（全部主题总览）或
  `nx-kv localtask get --id <n> --cwd "<目录>"`（单条；`status` 从 pending →
  consumed 即已被领取）。
- **改/撤**：`update --id <n> --text "<新内容>"` 改写；`remove --id <n>` 撤回。
- **完成怎么知道**：本机队列是单向投递，不回传执行结果——接收方完成后的产出
  在它的目录/对话里，由用户或那边的 agent 汇报。不要轮询本队列等「完成」状态，
  它没有这个状态。

## 五、常见错误与避坑

| 错误做法 | 后果 | 正确做法 |
| --- | --- | --- |
| `--cwd` 随手填或省略 | 任务排进错误/没人看的队列；省略时提交进**你自己的**目录 | 填接收方 agent 实际工作的目录；不确定先问 |
| 任务文本引用本对话（「如上所述」） | 接收方无从执行 | 自包含：目标/背景/注意写全，路径写全 |
| 把没和用户对齐的猜测提交出去 | 那边的 agent 按错误需求白干一轮 | 先确认再提交；提交前给用户过目 |
| 多行长文本直接塞 argv | 跨执行边界可能被切掉后半截（静默丢内容） | 单行 + ①②③ 编号；确要换行用引号包裹并提交后 `get` 核对 |
| 一条任务塞一整个项目 | 接收方要么做偏要么摆烂 | 拆成多条可独立完成的单元 |
| 提交后反复轮询队列等「完成」 | 队列没有完成状态，永远等不到 | 产出由用户/接收方汇报；本侧只管投递与查领取状态 |
| 没加 --json | 人读文本难解析 | agent 调用一律加 --json |
