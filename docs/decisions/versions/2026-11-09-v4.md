# 2026-11-09 · 存储版本 4 说明

- date: 2026-11-09
- version: 4
- migration: `src/core/db/migrations/v4.sql` + `v4-data.js`（DDL + 数据搬运同事务）
- tables: 新建 `group_refs`（group_key / ref_key / note / position / created_at）
- changes:
  - 参考仓库（type=ref）的绑定从**仓库级**升到**组级**：`group_refs` 两端都 FK
    `repos(key)`（ON DELETE/UPDATE CASCADE），PK `(group_key, ref_key)`。
    组内所有仓库共享组上绑定的参考仓库。
  - **明确不做继承**：没有「组绑定 + 仓库绑定叠加」，没有覆盖 / 排除 / 解绑表达式，
    读取时不产生「来自继承」的来源标记。`note` 只描述「这个组为什么参考它」。
  - 数据搬运（v4-data.js）：
    1. ref 侧 `ext_linked` 的 `{kind:'board'}` → 直接落 `group_refs`；
    2. ref 侧 `{kind:'repo'}` 与 dev 侧 `{kind:'ref'}`（含旧键 `ext_linked_refs`）
       → 解析目标仓库所属的**每个组**，各落一条；
    3. 同组同参考合并（note 取优先级最高的非空值：组级描述 > 仓库级描述）；
    4. 已迁移条目从 `ext` 删除；**无归属组的仓库的旧绑定原样保留**，不静默丢弃，
       `repo ref check` 会报「未迁移」（真实库迁移前为 0 条）。
  - 读取侧：`refsForRepo` 只按仓库所属组返回；`refsForBoard` 只读组绑定；
    `repo bind --repo` 解析到该仓库所属的每个组，无组显式报错；
    `repo ref note` 的 `--repo` 仅在仓库只属于一个组时可用。
- 迁移实测（真实库副本，迁移前 2026-11-09）：
  - 仓库级绑定 20 条（4 个仓库、0 个无组仓库）→ `group_refs` 22 条
    （组 nx 18 / csharp 2 / quickget 2；nx 组内两个仓库的 20→18 为去重）；
  - 迁移后 `ext_linked` 残余仓库级绑定 0 条；`repo ref of nx-pg / cs-wd` 输出与
    迁移前逐条等价（仅去掉仓库级重复）。
- 动机：参考仓库的语义单位是「领域组」而不是单个仓库；绑定在仓库上时，
  按组查看看不到参考（用户实际遇到的缺口）。

- 回滚：只允许向前升级，不提供降级脚本。迁移前备份由启动检查写
  `~/.nx-kv/backups/nxkv-<时间戳>.db`；v4 只新增表，旧库文件保留即可回退到旧版本程序
  （旧程序不认识 `group_refs`，会忽略它）。

## 补记（2026-11-09，口径更正）

上文的「只保留组级、仓库级残余 0 条」是 v4 迁移当时的**中间态**，不是最终模型。
用户随后澄清：**组级与仓库级绑定并存**，参考仓库也可以直接绑单个开发仓库
（存 `repos.ext.ext_linked` 的 `{kind:'ref'}`）。20 条被搬走的仓库级绑定已用
`repo ref backfill` 从 v3 快照精确补录回来，与 22 条 `group_refs` 并存；
本版本**不升 v5**（schema 形状未变），补录理由与逐条核对见
[../2026-11-09-repo-and-group-ref-bindings.md](../2026-11-09-repo-and-group-ref-bindings.md)。
