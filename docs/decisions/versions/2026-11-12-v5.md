# 2026-11-12 · 存储版本 5 说明

- date: 2026-11-12
- version: 5
- migration: `src/core/db/migrations/v5.sql`（DDL 重建 + 关系表快照回填）
- tables: 重建 `attachments`（新增 mdfile / external / 4 列 / 1 索引）
- changes:
  - `attachments.kind` 的 CHECK 扩为 `('file','url','task','ref','mdfile')`：
    `mdfile` = 「本地 .md 文件指针」，字节留在用户磁盘原地，库里只存路径与指纹。
  - `attachments.storage` 的 CHECK 扩为 `('','local','cloud','external')`：
    mdfile 固定 `external`。
  - 新增列（仅 mdfile 使用，其它 kind 留空/0）：
    `abs_path`（规范化绝对路径，唯一性基础）、`anchor_dir`（相对链接锚点 =
    登记时文件所在目录）、`missing_at`（上次确认文件不存在的时间）、
    `last_seen_at`（上次读到且 hash 未变的时间）。
  - 新增 `ux_attachments_mdfile_path`：`abs_path COLLATE NOCASE` 部分唯一
    （`kind='mdfile' AND deleted_at IS NULL`），同一外部文件只登记一行。
  - 既有 4 个索引（dedupe/kind/target/group）随表重建原样恢复。
- 重建方式：SQLite 不能 ALTER CHECK，只能 12-step 重建。**关键坑（实测）**：
  外键启用时 `DROP TABLE attachments` 会做一次隐式 DELETE，并**立即触发**
  `task_attach` / `ref_attach` 的 `ON DELETE CASCADE`；`PRAGMA defer_foreign_keys=ON`
  只推迟约束**校验**，不推迟级联**动作**，直接重建会把关系表静默清空
  （`foreign_key_check` 仍为干净）。因此 v5 在重建前用 `CREATE TEMP TABLE`
  快照两张关系表，重建后按显式列名回填，再 DROP 快照；失败仍由 migrator
  整步回滚。
- 迁移实测（真实库副本，2026-11-12）：
  - attachments 74 行（file 68 / task 3 / url 2 / ref 1）旧字段逐行一致；
  - `task_attach` 87 行、`ref_attach` 0 行，迁移前后逐行一致（87/87）；
  - `PRAGMA foreign_key_check` 空；
  - 同一路径在单测里另造 87 行关系验证（`tests/unit/mdfile-v5-migrate.test.mjs`）。
- 回滚：只允许向前升级。迁移前备份由启动检查写
  `~/.nx-kv/backups/nxkv-<时间戳>.db`；v5 只扩 CHECK 与新增列/索引，旧程序读写
  既有 kind 不受影响（新列被忽略），可直接回退到旧版本程序。
