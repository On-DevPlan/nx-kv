# context-layering — 长会话的分层上下文组织 SOP

> 归属 [[kv-submit]]。会话已经拉得很长（几十上百轮、关键信息散落各处），
> 要把会话保存下来交给其他 agent、或从中提炼需求时，先按本 SOP 组织上下文，
> 再走 [[submit-workflow]] 提交。

## 一、交接 = 换一个没有本会话记忆的读者

kv-submit 的本质是**会话交接**：接收方看不到本对话，任务文本必须把上下文
重新组织成它能独立使用的形态。这和 agent 延续自己的会话是同一个问题，
答案也一样：**分层组织，不要单层平铺**。

单层的两种翻车：

- 全搬流水账 → 接收方抓不住重点，对话里独有的信息被淹没；
- 只搬最近几轮 → 早期定下的决策/约束丢失，接收方做出早被否决的方案。

分层的解法：

```
[旧对话 E1…E8][最近对话 E9 E10]  →  [结构化摘要层 S1] + [最近原文层 E9 E10]
```

- **摘要层**（旧对话）：按固定模板组织成结构化事实，保证记忆槽位不缺；
- **原文层**（最近对话）：最近一两轮**逐字保留**——用户需求的原始措辞是
  第一手证据，不经转述。

两层各管一件事：摘要层保结构齐全，原文层保措辞保真。

## 二、摘要层：七个固定槽位

摘要不是自由发挥的笔记，是**固定槽位的结构化事实**——每个槽位回答一个
交接必备的问题，缺一个槽位就缺一类记忆：

| 槽位 | 回答的问题 |
| --- | --- |
| 目标 | 用户到底想完成什么（一两句） |
| 需求与约束 | 用户明说过的约束、偏好、范围边界 |
| 已定决策 | 定下来了什么、为什么 |
| 工作状态 | 做到哪了：已完成 / 进行中 / 被阻塞 |
| 下一步 | 接下来按什么顺序做什么 |
| 相关文件 | 接手要打开哪些路径，写全路径 + 为什么相关（最多 15 条，最重要的在前） |
| 关键上下文 | 什么事实缺了就干不了、对方又无法自行恢复 |

组织规则：

| 规则 | 做法 |
| --- | --- |
| 单行短句要点 | 不写段落、不嵌套列表 |
| 引用代替复述 | 对方能从代码/文件恢复的信息不搬，列路径即可 |
| 精确保留原文 | 路径、符号名、命令、报错字符串、URL、标识符一字不改 |
| 只带未解决的 | 用户问题：已被解决的删掉；未解决的保留原话措辞 |
| 带上工作流状态 | 未提交/已提交/已推送/在 review/已合并——决定对方从哪接手 |
| 环境信息不搬 | 仓库通用约定、CLAUDE.md/AGENTS.md 内容对方自己有；**对话独有的决策与偏好必须搬** |
| 输出只搬关键行 | 日志/命令输出摘关键结论，不整段贴 |
| 已否决 ≠ 已决策 | 被推翻的旧方案标注「已否决」或丢弃，不得混进「已定决策」 |
| 文本自包含 | 不出现「如前所述」「上文提到」——交接文本里没有「上文」 |

## 三、原文层：最近对话逐字保留

- 最近 1-2 轮对话（用户消息 + 助手回复）原样保留，不进摘要层；
- 用户最后几条消息的**原话**最重要——需求的第一手证据。进一次摘要是一次
  转述，组装进任务文本又是一次转述，两层转述就跑偏了；
- 拿不准某句是决策还是闲聊，回对话原文核对，不靠记忆复述。

## 四、交接层：两层组装成任务文本

任务文本是交给接收方的**交接层**，从上面两层逐段组装（①目标②背景③注意，单行）：

| 来源 | 去向 |
| --- | --- |
| 摘要层·目标 + 下一步 | ①目标 |
| 摘要层·需求与约束 + 已定决策 + 相关文件 + 关键上下文 | ②背景 |
| 摘要层·工作状态·已完成 | ②背景里写「已完成，不要重做」，或无必要则省略 |
| 摘要层·工作状态·被阻塞 + 已否决方案 | ③注意 |
| 原文层·未回答的用户问题（原话） | ③注意，标注「用户尚未回答」 |

逐段组装，不跳段——跳一段就是丢一块记忆。

## 五、交接文本的提示词构建

把两层组装成任务文本时，按四条要领构建——它们决定接收方拿到文本后
能不能正确「接」：

1. **开篇重定义任务**：第一句就让接收方明白这是**接手**，不是新开工。
   ①目标开头交代已有进度（「继续/接手…，已完成 X」），防止它从零重做。
2. **固定槽位 = 输出契约**：七槽位就是契约，缺一个槽位就是缺一类记忆。
   组装完对照第七节清单逐段核对，缺了就补，不带侥幸提交。
3. **消费侧说明**：明写接收方该怎么用这份交接——「已完成 X，不要重做」；
   未答问题标「用户尚未回答」；带原文引用的地方是第一手证据，可放心依据。
4. **禁区前置**：③注意先写「不要做什么」，再写坑——禁令比描述更防跑偏。

## 六、会话继续增长后再组织

交接不是一次性的：给同一个目标分多轮补任务、或会话又聊了一段需要重新
组织时，按同一套架构迭代：

- **新事实永远优先于旧摘要**：旧信息保留，除非新对话明确推翻、取代或解决了它；
- 重新对工作状态：完成的从「进行中」移出；已解决的阻塞、已回答的问题删掉；未解决的继续保留；
- 已不再服务于「接着干」的信息可以删——组织为续做服务，不为存档服务。

## 七、交接前校验清单

- [ ] 路径全部是全路径且真实存在
- [ ] 报错/命令/符号名与对话原文逐字一致
- [ ] 「已定决策」里没有混入被否决方案
- [ ] 用户未回答的问题原话保留并标注
- [ ] 工作流状态（提交/推送与否）写清了
- [ ] 「如上所述」「刚才那个」零出现
- [ ] 给用户过目后再 `localtask add`

## 八、常见错误

| 错误 | 后果 | 正确做法 |
| --- | --- | --- |
| 会话很长还直接提炼，不分层 | 早期决策/约束静默丢失 | 先分两层（摘要 + 原文），再组装任务文本 |
| 摘要层写成流水账 | 任务文本超长，接收方抓不住重点 | 七个固定槽位 + 单行要点，无关支线不搬 |
| 报错/路径凭记忆转述 | 对方按错误信息排查半天 | 精确保留原文，拿不准回对话核对 |
| 用户原话被两轮转述 | 需求失真，做出来的不是要的 | 最近对话逐字保留，未答问题带原话 |
| 已否决方案混进背景 | 对方做出被否决的方案 | 已否决的进 ③注意 或丢弃 |
| AGENTS.md/通用约定大段搬进任务 | 文本膨胀，独有信息被稀释 | 只搬对话独有的决策、偏好、事实 |
