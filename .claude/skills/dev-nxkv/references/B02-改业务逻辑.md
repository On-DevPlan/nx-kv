# B02 · server · 改已有业务逻辑

> 序列 B（server）。入口不变、入参不变，只改「算出来的结果」：判定、事务、错误码、派生字段。
> **先找唯一实现，再在那一处改**——同一个判断出现两遍就是下一次不一致的起点。

## ① 前置（先跑，拿事实）

```powershell
node bin/kv.mjs routes --module <模块>                 # 这个域的入口清单（先确认要改的行为从哪个入口进去）
grep -n "^export" src/modules/<模块>/service.ts         # 业务函数有哪些
ls src/modules/<模块>/repo/                             # SQL 在哪些文件
grep -rn "<业务名词>" src/modules/<模块> --include=*.ts | head -20   # 这个判断现在出现在几处
ls tests/unit | grep "<模块>"                           # 已有用例（没有 = 这是新行为，要补）
```

判断「改哪一层」：

| 现象 | 落在 |
|---|---|
| 结果算错、边界没判、错误码不对 | `service.ts`（或 `mutator/validate.ts`） |
| 查出来的行不对、漏了 `deleted_at IS NULL`、排序不稳 | `repo/*.ts` |
| 只是参数没透传 / 缺一个可选参数 | action 声明（走 `B01-加一条命令.md`） |
| Node 与浏览器都要用的纯计算 | `src/shared/`（纯函数，零依赖） |
| 时间戳、路径、错误类型等原语 | `src/core/`（不含业务名词） |

## ② 动作

1. **定位唯一实现**，把重复的判断合并掉：

```powershell
grep -rn "<函数名>\|<判定关键词>" src/modules --include=*.ts | head -20
```

2. **改在 service 层，action 只编排**。错误用 `src/core/errors.ts` 的 `badInput` / `notFound` / `conflict`，不要 `throw new Error(...)`（错误码会退化成 500/1）。

3. **多表写入必须在一个事务里**：

```powershell
grep -rn "tx(" src/modules/<模块>/service.ts | head -5        # 通用模块：core/db/tx.ts 的 tx
grep -n "withTopicMutator" -A 10 src/modules/localtask/writes.ts | head -16   # localtask 的唯一写入口
```

- 通用模块：`tx((db) => { … })`，回调**保持同步**；需要 `await` 的（git/fs/网络）在事务外先取。
- `localtask` 域：**所有 `tasks` / `topics` 写入必须经 `withTopicMutator`**——它负责派生字段、事件、快照同步，绕过就是静默不一致。

4. **派生字段不手写**：任务 DAG、`ready`、`blockBy` 的另一侧由 `syncNewTaskDag` / `syncTaskDagUpdate` / `markTaskSuccess`（`src/modules/localtask/writes.ts`）维护，改行为时同步改它们而不是在调用方补 UPDATE。

5. **补一条钉住行为的用例**（改行为却没改测试 = 没有回归防线）：

```powershell
ls tests/unit | grep "<模块>"
node --import tsx --test tests/unit/<域>-<行为>.test.mjs
```

6. **同步注释与决策**：`service.ts` 顶部的「读写口径」注释如果与新行为不符，一并改；动了语义取舍就补 `docs/decisions/`。

## ③ 自检

```powershell
pnpm typecheck
node --import tsx --test tests/unit/<域>-*.test.mjs
pnpm lint
node bin/kv.mjs <域> <命令> --json          # 真跑一次，看新行为
```

| 检查 | 通过判据 |
|---|---|
| 行为正确 | 目标场景返回预期；边界值（空、0、已删除、跨队列）逐个走过 |
| 错误语义 | 非法输入返回结构化错误码，不是 500 / 崩溃 |
| 唯一实现 | 同一判断只存在一处（`grep` 复核） |
| 派生一致 | 改完 `localtask chain` / `localtask list --json` 与库内数据一致 |
| 回归 | 该域既有用例全绿；新增行为有用例 |

## ④ 失败分支

| 症状 | 原因 | 处置 |
|---|---|---|
| 改了 service 但接口行为没变 | 另有第二条实现（action 里也写了一份） | `grep` 同一关键词，合并到 service |
| `tx` 抛 `TypeError` | 回调返回了 Promise（里面有 `await`） | 事务外取数据，事务内只做同步写 |
| 写入成功但派生字段没更新 | 绕过了 `withTopicMutator` | 改回唯一写入口 |
| 任务永远不 ready | 判定读了已删除/已取消的行 | 判定前过滤终态；删除时同步清边 |
| 错误码从 400 变成 500 | 用了普通 `Error` | 换 `badInput` / `notFound` / `conflict` |
| 单测单独跑过、全量跑挂 | 用例之间共享了库或全局状态 | 用 `tests/support/test-store.mjs` 的临时库 |
| 界面数字与接口不一致 | 前端自己又算了一遍 | 判定只留后端，前端只渲染接口结果 |

## ⑤ 反模式

- 在 SQL 里写业务判断（「完成则 ready」这类属于纯函数层）。
- 同一个规则在 service、repo、前端各写一遍。
- 为了方便在 `repo/*.ts` 里顺手 `await` 外部 IO（事务边界会被打穿）。
- 改行为时顺手放宽约束来「让用例过」。
